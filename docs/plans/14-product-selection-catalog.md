# Сценарии подбора продукта через каталог: план реализации

> **Для исполнителей:** обязательный навык: superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans — выполнять план по задачам. Шаги отмечаются флажком (`- [ ]`).
>
> **Статус: ЧЕРНОВИК — не исполнять до приёма на Г3a и отдельного «поехали» владельца.**

**Цель:** подключить каталог к ядру и реализовать оба принятых сценария R1a/R1b — подбор по названию известного продукта с уточнением недостающих слотов и рекомендацию вариантов, когда клиент не знает продукт.

**Тикет:** `.scratch/support-agent/issues/14-product-selection-catalog.md`

**Спецификация:** `.specs/support-agent.md` (копия трекера: `.scratch/support-agent/spec.md`), требования R1a и R1b; ADR-0010 (структурный поиск каталога), ADR-0014 (формат ответа и режимы эскалации), ADR-0015 (две сценария и разрыв реализации).

**Контракт:** `docs/api-contract.md` §1, §5 (контракт ядра), §4 (контракт веб-чата). **Данные:** `docs/data-model.md` §3.2 (`conversations`), §3.4 (`products`), §3.9 (`catalog_snapshots`).

**Технологии:** Node.js 22 LTS, TypeScript, PostgreSQL 16 + pgvector, Vitest.

## Команда проверки

`npm run test -- tests/core/catalog-lookup.test.ts tests/core/run.test.ts tests/api/chat.test.ts`

Плюс отдельный живой прогон обоих сценариев через веб-чат — свидетельство фиксируется в отчёте среза.

## Общие ограничения

- Код создаётся только в спринте 26.11 19:00 → 28.11 19:00 по Камчатке, после Г3a и отдельного «поехали».
- Срез владеет: `src/core/catalog-lookup.ts`, `src/core/slots.ts`, миграцией `5300_conversation_slots.sql`, тестами `tests/core/catalog-lookup.test.ts`.
- Общие поверхности не меняются без координации exec: `docs/api-contract.md`, `docs/data-model.md`, `src/modules/catalog/**`, `src/modules/knowledge/**`, роутер, `package.json`, `tsconfig.json`, `next.config.ts`, `vitest.config.ts`.
- Миграция этого среза — `5300_conversation_slots.sql`. Номер закрепляет exec (диапазон волны 2: 6000–6999; 5300 занят каналами, поэтому слоты идут в свободный 53xx — при согласовании с exec номер меняется на 53xx без изменения содержимого).
- Импорт фида и обход сайта не запускаются одновременно — тяжёлые прогоны выполняет exec по одному.
- Пул тестовых процессов ограничен: `vitest --pool=forks --poolOptions.forks.maxForks=2`.

## Шаги

### Шаг 1. Миграция состояния слотов

- [ ] Создать `db/migrations/5300_conversation_slots.sql`: таблица `conversation_slots (conversation_id uuid → conversations(id), slot text, value text, updated_at timestamptz)`, первичный ключ `(conversation_id, slot)`, ограничение на `slot IN ('quantity','termMonths','deployment','vendor')`, `ON DELETE CASCADE`.
- [ ] Применить: `npm run db:migrate:up` → в выводе `применено: 5300_conversation_slots.sql`.
- [ ] Проверить откат: `npm run db:migrate:down` → таблица исчезает; затем применить снова.

### Шаг 2. Извлечение слота и названия продукта из сообщения

- [ ] **Падающий тест** `tests/core/catalog-lookup.test.ts`: `extractProductQuery("Нужен MDaemon Standard")` → `"mdaemon standard"`; `extractProductQuery("Сколько стоит?")` → `null`; `extractSlots("нужно 50 лицензий на 12 месяцев в облаке")` → `{ quantity: 50, termMonths: 12, deployment: "облако" }`.
- [ ] Создать `src/core/catalog-lookup.ts` с типами `RequirementSlots`, `extractProductQuery`, `extractSlots`, `extractVendor`.
- [ ] **Зелёный тест:** `npx vitest run tests/core/catalog-lookup.test.ts` → все тесты проходят.

### Шаг 3. Поиск позиции каталога и карточка

- [ ] **Падающий тест**: фикстура каталога (две позиции MDaemon на 50 и 100 пользователей, одна Dr.Web на 50 ПК) → `lookupCatalog("Нужен MDaemon Security Gateway", слоты)` возвращает позицию MDaemon с ценой больше нуля и ссылкой на `store.softline.ru`.
- [ ] Реализовать `lookupCatalog`: вызов публичного `catalog.search` + `catalog.getByOfferId`, извлечение вендора из списка вендоров каталога, сборка `CatalogMatch`.
- [ ] Сортировка: позиции, закрывающие собранные слоты, идут первыми; внутри группы — по близости количества к запрошенному, затем по цене.
- [ ] Ответ `catalogAnswer` и `catalogMatchText`: цена из карточки, пометка «из снимка фида», ссылка на карточку. Числа не приходят из ответа модели.
- [ ] **Зелёный тест.**

### Шаг 4. Уточняющий вопрос при недостатке данных

- [ ] **Падающий тест**: `lookupCatalog("Нужен MDaemon Security Gateway", без слотов)` → `missingSlots` содержит `quantity`; ответ содержит один вопрос о количестве и не содержит рекомендации позиции.
- [ ] Реализовать `missingSlots`, `SLOT_QUESTIONS`: порядок вопросов — количество, срок лицензии, тип развёртывания. Задаётся один вопрос за ход.
- [ ] В ядре (`src/core/run.ts`) узел `catalog` при непустом `missingSlots` возвращает `respond` с вопросом и найденными позициями в перечне, без выбора варианта.
- [ ] **Зелёный тест.**

### Шаг 5. Сохранение слотов по диалогу

- [ ] **Падающий тест**: `saveSlots(conversationId, { quantity: 50 })`, затем `saveSlots(conversationId, { termMonths: 12 })` → `loadSlots` возвращает оба значения; `deployment` остаётся `null`.
- [ ] Создать `src/core/slots.ts`: `loadSlots`, `saveSlots`. Значения лежат в базе, а не в памяти процесса.
- [ ] В ядре: слоты читаются в начале диалога, новые значения из текста дополняют сохранённые, результат сохраняется.
- [ ] Изоляция: слоты диалога не видны другому `conversation_id` и другому `tenant_id` — проверяется тестом.
- [ ] **Зелёный тест.**

### Шаг 6. Подбор при неизвестном продукте

- [ ] **Падающий тест**: `lookupCatalog("защита почты для 50 сотрудников", { quantity: 50 })` возвращает несколько позиций с разными `offer_id`.
- [ ] Реализовать извлечение требований без названия продукта: слова запроса и числа не попадают в название позиции, а в слоты; количество из текста идёт в слот `quantity`.
- [ ] Ответ содержит 2–3 различимых варианта с ценой из карточки и ссылкой на каждую позицию; обоснование — из названия, вендора и параметров карточки, а не из ответа модели.
- [ ] Если подходящих позиций нет — честный ответ об отсутствии (режим `off` по ADR-0014), без выдуманных вариантов.
- [ ] **Зелёный тест.**

### Шаг 7. Проверка через общий API ядра

- [ ] **Падающий тест** в `tests/core/run.test.ts`: три ветки через `runAgent` — известный продукт с полными данными (`outcome: respond`, источник `catalog_product`, цена в тексте, ссылка); известный продукт без количества (`outcome: respond`, в тексте один вопрос о количестве, рекомендации нет); неизвестный продукт (`outcome: respond`, две-три позиции).
- [ ] **Падающий тест** в `tests/api/chat.test.ts`: `POST /v1/chat` с теми же входами даёт тот же результат через HTTP-контракт.
- [ ] **Падающий тест** в `tests/api/chat.test.ts`: второй запрос с тем же `conversation_id` продолжает сбор слотов — первый ответ задаёт вопрос о количестве, второй запрос с ответом на вопрос даёт карточку с ценой и ссылкой, а слот `quantity` в базе обновляется. Без этого кейса AC 5 (продолжение по `conversation_id`) не проверяется.
- [ ] Убедиться, что трасса содержит узел `catalog` с `matches` и `missingSlots`, а источники ответа имеют вид `catalog_product` со ссылкой на карточку.
- [ ] **Зелёный тест:** команда проверки среза проходит целиком.

### Шаг 8. Живой прогон и свидетельства

- [ ] Живой прогон через веб-чат (`http://127.0.0.1:3000/widget`): «Нужен MDaemon Security Gateway» → уточняющий вопрос о количестве; ответ на вопрос → карточка с ценой и ссылкой; «защита почты для 50 сотрудников» → 2–3 варианта с ценами.
- [ ] Живой прогон через MAX: тот же вопрос боту, ответ приходит в чат.
- [ ] Сохранить свидетельства без секретов и без реальных персональных данных: пример трёх веток, вывод команды проверки, фрагмент трассы с узлом `catalog`.
- [ ] Проверить, что цены в ответе совпадают с карточкой каталога, а не с придуманными моделью числами.

## На что обратить внимание при проверке

- Каталог — датированный снимок фида заказчика. Цена и наличие не подаются как подтверждённые в реальном времени: в ответе это помечено прямо.
- Суммы считает код по карточке. Модель отвечает только за текст, и её числа сверяются валидатором с источниками.
- Поиск по названию устойчив к лишним словам запроса: «MDaemon Standard» находит «MDaemon», потому что слова запроса соединяются через «ИЛИ», а порядок задаёт число совпавших слов.
- Слоты накапливаются по диалогу: ответ клиента на уточняющий вопрос дополняет состояние, а не начинает с нуля.
- Модель эмбеддингов фиксируется в чанке, и поиск отвергает чанк, проиндексированный другой моделью: вектор запроса и вектор чанка должны быть сравнимы.
- Режим эскалации (`ESCALATION_MODE`) задаётся окружением: `off` — честный ответ без очереди менеджера, `notice` — уведомление клиенту, `on` — поведение R4. Сценарии подбора от режима не зависят.

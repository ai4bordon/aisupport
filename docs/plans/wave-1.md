# Волна 1: шесть параллельных срезов — пакет планов

> Статус: **ЧЕРНОВИК для Г3a.** План волны: шесть срезов выполняются параллельно, каждый в своём каталоге.
> Основание: распоряжение владельца о максимальном распараллеливании вертикальных слайсов.

## 1. Правила волны

### 1.1 Замороженные поверхности

Контракт замораживается до начала волны 1. Поверхности, которые нельзя менять внутри среза:

| Поверхность | Владелец | Как менять |
|---|---|---|
| `docs/api-contract.md` | exec | Только через exec, с записью в журнал решений и пометкой ревизии |
| `docs/data-model.md` | exec | Только через exec |
| Схема миграций: имена и номера файлов | exec | Номера закрепляет exec до старта среза |
| Роутер и корневая конфигурация приложения | exec | Правки после слияния волны |
| Ядро агента `src/core/**` | срез «ядро» | Другие срезы не правят, обращаются через порты |

Агент, который считает, что поверхность требует правки, останавливается и передаёт вопрос exec. Самовольная правка контракта запрещена.

### 1.2 Владение файлами

Один агент — один каталог. Агент не правит файлы вне своего списка, даже если они ему мешают.

| Срез | Свой каталог | Общие файлы, которые агент НЕ трогает |
|---|---|---|
| Ядро | `src/core/**`, `src/db/**`, `src/contracts/**`, `src/app/api/chat/**`, `src/app/api/agent/**`, `src/app/api/health/**`, `src/app/api/kb/**`, `src/app/widget/**`, `src/modules/knowledge/index.ts`, `src/modules/knowledge/search.ts`, `src/modules/policy/**`, `src/modules/telemetry/**` | `next.config.ts`, `package.json`, `tsconfig.json`, `vitest.config.ts`, чужие каталоги |
| Импорт фида | `src/import/catalog/**`, `src/modules/catalog/**`, `scripts/import-feed.ts` | то же |
| Импорт базы знаний | `src/import/knowledge/**`, `scripts/import-docs.ts` | то же |
| Документы | `src/modules/documents/**`, `src/app/api/docs/**` | то же |
| Доступ к стенду | `src/modules/access/**`, `src/modules/limits/**`, `src/app/access/**`, `src/app/api/access/**` | то же |
| MAX-адаптер | `src/channels/max/**`, `src/app/api/max/**` | то же |

Общие файлы (`package.json`, `tsconfig.json`, `next.config.ts`, `vitest.config.ts`) правятся только exec после слияния волны. Агент, которому нужна новая зависимость, записывает её в свой раздел отчёта и не правит `package.json`.

### 1.3 Диапазоны миграций

Номера закрепляет exec. Агент не выбирает номер миграции.

| Срез | Диапазон | Номера |
|---|---|---|
| Ядро | 100–999 | 100 `extensions`, 110 `tenants`, 120 `conversations`, 130 `knowledge_core`, 140 `escalations_promises`, 150 `policy_rules`, 160 `audit` |
| Импорт фида | 1000–1999 | 1000 `catalog`, 1010 `clients_orders_licenses` |
| Импорт базы знаний | 2000–2999 | 2000 `kb_sources` |
| Документы | 3000–3999 | 3000 `templates_documents` |
| Доступ к стенду | 4000–4999 | 4000 `usage_counters` |
| MAX-адаптер | 5000–5999 | 5000 `channel_state` |
| Волна 2 | 6000–6999 | 6000 `agent_settings`, 6100 `analytics` |

Миграция создаётся только владельцем соответствующей таблицы. Запись в чужую таблицу разрешена; создание и изменение чужой таблицы — нет.

### 1.4 Порты между срезами

Срезы волны 1 не импортируют код друг друга. Связь идёт через замороженный контракт.

| Порт | Владелец реализации | Кто вызывает | Форма |
|---|---|---|---|
| Ядро: `runAgent(input: NormalizedMessage): Promise<AgentOutcome>` | срез «ядро» | срез MAX (в волне 2), срез «тень» (волна 2) | Порт внедряется в срез-клиент как параметр; в волне 1 срезы, которым ядро нужно, собирают собственную сборку и получают ядро по HTTP-контракту `/agent/run` |
| Доступ: `checkAccess(request): Promise<AccessDecision>` | срез «доступ» | срез «ядро» | Подключается exec в волне 2 при слиянии; в волне 1 срез «доступ» проверяет себя собственными тестами |
| Каталог: `catalog.search(query, filters)` | срез «импорт фида» | срез «документы» (волна 2), ядро (волна 2) | Данные лежат в таблице `products`; срез «документы» в волне 1 принимает готовую структуру расчёта на вход и не зависит от кода каталога |
| Документы: `renderQuote(quote: QuoteInput): Promise<RenderedDocument>` | срез «документы» | ядро (волна 2) | Чистая функция от структуры, описанной в контракте |
| Эмбеддинги: HTTP-эндпоинт и формат ответа | заморожены в контракте | срез «ядро» (поиск), срез «импорт базы знаний» (нарезка) | Каждый срез реализует свой тонкий клиент по замороженной спецификации; дублирование клиента осознанное — ради независимости срезов |

### 1.5 Ресурсы машины

Стенд разработки: 4 vCPU, 8 ГБ. Параллельные тяжёлые операции машину уронят.

| Правило | Как соблюдать |
|---|---|
| Импорт фида и обход сайта — в одном окне | Обе операции запускает exec последовательно, не одновременно |
| Тяжёлые прогоны — по одному | Прогон с реальным фидом и обходом сайта запускает только exec, остальные агенты — юнит-тесты |
| Юнит-тесты агента | Пул процессов ограничен: `vitest --pool=forks --poolOptions.forks.maxForks=2` |
| Память | Импорт фида читает файл потоково; загрузка 292 МБ в память запрещена |
| Интеграционные тесты | Только у exec после слияния волны |

### 1.6 Проверка

- Юнит-тесты среза — у агента, команда и код завершения в отчёте.
- Интеграционные тесты — у exec после слияния волны.
- Г3b по каждому срезу: diff в границах каталога, команда проверки, код завершения.

## 8. Порядок слияния

1. Каждый агент сдаёт свой срез: юнит-тесты, код завершения, список изменённых файлов, замечания к общим поверхностям.
2. Exec проверяет границы: diff агента не выходит за его каталог.
3. Exec выполняет интеграционные тесты волны: срез «ядро» + импорт фида + импорт БЗ + документы + доступ + MAX.
4. Exec вносит общие правки: роутер, корневой конфиг, подключение барьера доступа и MAX к ядру.
5. Exec запускает тяжёлые операции последовательно: импорт фида, затем обход сайта.

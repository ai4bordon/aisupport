# Режим тени в веб-чате и MAX: план реализации

> **Для исполнителей:** обязательный навык: superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans — выполнять план по задачам. Шаги отмечаются флажком (`- [ ]`).
>
> **Статус: ЧЕРНОВИК — не исполнять до приёма на Г3a и отдельного «поехали» владельца.**

**Цель:** сделать режим тени одной управляемой настройкой для веб-чата и MAX: каждый новый запрос в тени сохраняет проверенный результат в очереди менеджера, но не отправляет клиенту ни ответа, ни уведомления об эскалации.

**Тикет:** `.scratch/support-agent/issues/06-shadow-mode.md`

**Спецификация:** `.specs/support-agent.md` (копия трекера: `.scratch/support-agent/spec.md`), требование R10; `adr/0008-shadow-mode.md`. Канонический контракт режима тени — `docs/api-contract.md` §4.

**Контракт:** `docs/api-contract.md` §1 (единая точка арендатора), §4 (веб-чат и режим тени), §5 (результат ядра), §6 (MAX). **Данные:** `docs/data-model.md` §3.1 (`tenants.shadow_mode`), §3.2 (`conversations`), §3.4 (`escalations`), §3.18 (`agent_steps`).

**Данные и реальное состояние:** настройка уже хранится в `tenants.shadow_mode` (`db/migrations/110_tenants.sql`); MAX-адаптер уже имеет порт `shadowMode: () => Promise<boolean>` и подавляет отправку в `src/channels/max/adapter.ts`. В MAX отключение реализовано только как чтение дублирующего поля `channel_state.shadow_mode`. В веб-чате `src/app/api/chat/route.ts` режим тени пока не учитывает. Таблица `escalations` создана в `db/migrations/140_escalations_promises.sql` и пока хранит причину, резюме, черновик и источники, но не имеет явного канала, результата и безопасной ссылки на трассу.

**Технологии:** Node.js 22 LTS, TypeScript, PostgreSQL 16, Vitest.

## Команда проверки

`npm run test -- tests/integration/06-shadow-mode.test.ts`

Команда собирает интеграционный сценарий среза: общий переключатель, подавление ответа в веб-чате и MAX, очередь менеджера и влияние отключения на новую обработку.

## Общие ограничения

- Срез владеет: `src/core/shadow-mode.ts`, `db/migrations/6300_shadow_mode_queue.sql`, `tests/shadow-mode/settings.test.ts`, `tests/integration/06-shadow-mode.test.ts`; согласованные изменения в `src/app/api/chat/route.ts`, `src/app/api/max/status/route.ts`, `src/channels/max/adapter.ts`, `src/channels/max/state.ts`, `src/channels/max/types.ts`, `src/channels/max/index.ts`, `scripts/max-worker.ts` и связанных тестах `tests/channels/max/send.test.ts`, `tests/integration/05-max-polling-adapter.test.ts`.
- Единственный источник истины — `tenants.shadow_mode`. Дублирующее `channel_state.shadow_mode` удаляется миграцией, а чтение и запись настройки идут через один сервис; значение кэшируется в процессе нельзя, потому что переключение должно влиять на новую обработку без перезапуска.
- Общие поверхности не меняются без координации exec: `docs/api-contract.md`, `docs/data-model.md`, `src/core/*` кроме явно оговорённого `src/core/shadow-mode.ts`, `src/core/run.ts`, роутер вне перечисленных выше маршрутов, `package.json`, `tsconfig.json`, `next.config.ts`, `vitest.config.ts`.
- Миграция среза — `db/migrations/6300_shadow_mode_queue.sql`. Номер закрепляет exec в диапазоне волны 2: 6000–6999; при конфликте exec меняет только номер, содержимое сохраняется.
- Пул тестовых процессов ограничен: `vitest --pool=forks --poolOptions.forks.maxForks=2`.
- Живой прогон выполняется после зелёного интеграционного теста и не подменяет его.

## Связь критериев приёмки с шагами

| AC | Что проверяет | Шаги |
|---|---|---|
| 1 | При включённой тени обычный результат сохраняется черновиком в очереди менеджера; веб-чат не отправляет ответ клиенту | 1, 2, 5, 6, 7 |
| 2 | При включённой тени MAX не вызывает `POST /messages`; вместо отправки записывается черновик/эскалация | 1, 3, 5, 6, 7 |
| 3 | Отключение влияет только на новую обработку: подтверждённый и проверенный ответ можно отправить, но эскалация остаётся без отправки | 2, 3, 4, 6, 7 |
| 4 | Запись очереди содержит канал, диалог, причину/результат и безопасную ссылку на трассировку | 1, 5, 6, 7 |

## Шаги

### Шаг 1. Миграция и единое хранение настройки режима тени

- [ ] **Падающий тест** в создаваемом `tests/shadow-mode/settings.test.ts`: после применения миграции `SELECT shadow_mode FROM tenants WHERE id = $1` возвращает текущее значение; новая запись очереди принимает `channel`, `result`, `trace_ref`, а колонка `channel_state.shadow_mode` отсутствует. До миграции тест падает из-за отсутствующих колонок.
- [ ] Создать `db/migrations/6300_shadow_mode_queue.sql`:
  - `ALTER TABLE escalations ADD COLUMN channel text NULL`, затем перенести значение из `conversations.channel`, удалить `NULL`, добавить `CHECK (channel IN ('web', 'max'))`;
  - добавить `result text NULL`, перенести в него `COALESCE(draft, summary)`, затем сделать `NOT NULL`;
  - добавить `trace_ref uuid NULL`, заполнить его `conversation_id`, затем сделать `NOT NULL REFERENCES conversations(id)`;
  - создать индекс `escalations_tenant_channel_status_created_at_idx ON escalations (tenant_id, channel, status, created_at DESC)`;
  - удалить `channel_state.shadow_mode` (сначала `DROP COLUMN IF EXISTS`), поскольку каноническая настройка находится в `tenants.shadow_mode`;
  - в Down-восстановлении вернуть удалённую колонку с `NOT NULL DEFAULT false`, восстановить `channel_state.shadow_mode`, убрать новые поля и индекс.
- [ ] Создать `src/core/shadow-mode.ts` — общий сервис с публичным API:
  - `isShadowMode(pool, tenantId): Promise<boolean>` — читает только `tenants.shadow_mode` для арендатора;
  - `recordShadowDraft(pool, input): Promise<string>` — создаёт запись `escalations` с `reason='shadow_mode'`, `summary`, `result`, `sources`, `channel`, `conversation_id` и `trace_ref` и возвращает UUID записи;
  - тип `ShadowDraftInput` содержит `tenantId`, `conversationId`, `channel: 'web' | 'max'`, `summary`, `result`, `sources`, `traceRef`; секреты, сырые ПД и полный payload трассы в него не принимаются.
- [ ] Применить: `npm run db:migrate:up` → в выводе `применено: 6300_shadow_mode_queue.sql`.
- [ ] Проверить откат: `npm run db:migrate:down` → новые поля и `channel_state.shadow_mode` возвращаются в исходное состояние; затем снова применить миграцию.
- [ ] **Зелёный тест:** `npx vitest run tests/shadow-mode/settings.test.ts` → тесты хранения, изоляции по `tenant_id` и отката проходят.

### Шаг 2. Подавление ответа веб-чата и запись черновика

- [ ] **Падающий тест** в `tests/shadow-mode/settings.test.ts` или создаваемом `tests/api/shadow-chat.test.ts`: при `tenants.shadow_mode=true` `POST /v1/chat` для вопроса с подтверждённым источником возвращает `outcome=escalate`, `answer=null`, `escalation.draft` содержит подготовленный ответ, а в `messages` отсутствует новая запись `role='agent'` с клиентским текстом ответа.
- [ ] **Падающий тест** проверки очереди: в `escalations` появляется одна запись с `channel='web'`, правильным `conversation_id`, `reason='shadow_mode'`, непустым `result`, равным сохранённому черновику, и непустым `trace_ref`.
- [ ] Изменить `src/app/api/chat/route.ts`: до запуска `runAgent` считать `shadowMode = await isShadowMode(pool, tenantId)` и зафиксировать это значение на время текущей обработки; при `respond` не вставлять клиентское сообщение в `messages` и не возвращать текст клиенту, а преобразовать проверенный ответ в эскалацию тени через `recordShadowDraft`; источники ответа сохранять в `sources`, а `trace_ref` брать из безопасного идентификатора диалога/трассы текущего `runAgent`.
- [ ] В веб-ответе сохранить технический `outcome=escalate` и `answer=null` по `docs/api-contract.md` §4; черновик и результат не должны попасть в клиентский текст.

### Шаг 4. Отключение действует только на новую обработку

- [ ] **Падающий тест** в `tests/shadow-mode/settings.test.ts`: сначала включить тень и создать одну обработанную запись очереди; затем выключить `tenants.shadow_mode`; следующий запрос с подтверждённым источником в веб-чате возвращает `respond`, а следующее событие MAX вызывает `sendMessage` ровно один раз. Ранее созданная запись очереди остаётся открытой и не удаляется.
- [ ] **Падающий тест** на границу момента переключения: если режим выключен после начала текущей обработки, текущая обработка всё равно завершается по снятому в начале значению; изменить режим можно только последующим запросом.

## На что обратить внимание при проверке

- Режим тени — общий переключатель, а не два независимых флага. `tenants.shadow_mode` и `channel_state.shadow_mode` не должны расходиться; второе поле удаляется.
- Отключение не удаляет и не «отправляет» ранее созданные черновики. Оно разрешает отправку только в новых обработках, прошедших policy/source/numeric/PII-проверки.
- Обычная эскалация остаётся эскалацией: наличие черновика в очереди не превращает её в разрешение отправить ответ клиенту.
- В тени запрещены все исходящие клиентские сообщения, включая нейтральное уведомление об эскалации, а не только основной ответ.
- Очередь не должна дублироваться: один результат ядра даёт одну запись очереди на один канал и диалог.
- «Безопасная ссылка на трассу» — только идентификатор UUID/ссылка на трассу диалога; полные внутренние журналы, токены и сырые ПД в очередь не попадают.
- MAX должен читать настройку на каждое событие, а веб-чат — на каждый HTTP-запрос; кэш процесса сделал бы отключение недействующим до перезапуска.

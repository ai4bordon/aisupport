# Учёт утверждённых обещаний клиентам: план реализации

> **Для исполнителей:** обязательный навык: superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans — выполнять план по задачам. Шаги отмечаются флажком (`- [ ]`).
>
> **Статус: ЧЕРНОВИК — не исполнять до приёма на Г3а и отдельного «поехали» владельца.**

**Цель:** принимать обязательство перед клиентом только из подтверждённого источника, сохранять его вместе с диалогом, сроком, ответственным и статусом, а менеджеру показывать журнал открытых, выполненных и просроченных обещаний — без внешних интеграций напоминаний.

**Тикет:** `.scratch/support-agent/issues/07-promises.md`

**Спецификация:** `.specs/support-agent.md` (копия трекера: `.scratch/support-agent/spec.md`), требование R11; ADR-0014 (режимы эскалации и запрет неподтверждённых обещаний).

**Контракт:** `docs/api-contract.md` §1 (единый HTTP API и публичные `index.ts` модулей), §3 (маршрут `GET /promises`), §4 (маршрут веб-чата `POST /v1/chat`), §9 (контракт эскалации). **Данные:** `docs/data-model.md` §3.4 (`escalations`), §3.5 (`promises`).

**Технологии:** Node.js 22 LTS, TypeScript, PostgreSQL 16, Vitest, Next.js Route Handlers.

## Команда проверки

`npm run test -- tests/integration/07-promises.test.ts`

Плюс отдельный живой прогон через веб-чат и очередь менеджера — свидетельство фиксируется в отчёте среза.

## Общие ограничения

- Код создаётся только в спринте 26.11 19:00 → 28.11 19:00 по Камчатке, после Г3a и отдельного «поехали».
- Реальное состояние схемы проверено командой `docker exec support-agent-pg psql -U postgres -d support_agent -c "\d promises"`: таблица `promises` уже создана миграцией `140_escalations_promises.sql` и содержит `id`, `tenant_id`, `conversation_id`, `text`, `due_at timestamptz NOT NULL`, `owner text NOT NULL`, `status text NOT NULL DEFAULT 'open' CHECK (status IN ('open','done','overdue'))`, `reminded_at`, `created_at` и индекс `(tenant_id, status, due_at)`. Поэтому колонки срока, ответственного и статуса **не дублируются и не переименовываются** — они уже покрывают AC 1; миграция волны 2 добавляет только недостающий провенанс подтверждённого источника и явную пометку синтетической записи.
- Миграция этого среза — `db/migrations/6500_promises_provenance.sql` (номер закрепляет exec, диапазон волны 2: 6000–6999; при согласовании с exec номер меняется на свободный 6xxx без изменения содержимого).
- Срез владеет: `db/migrations/6500_promises_provenance.sql`, новым модулем `src/modules/promises/` (`index.ts` — единственная публичная точка входа), новым ядровым модулем `src/core/promise-extract.ts`, маршрутом `src/app/api/promises/route.ts`, тестами `tests/core/promise-extract.test.ts` и `tests/integration/07-promises.test.ts`.
- Точечные изменения в общих файлах допускаются только в `src/core/run.ts` (передача подтверждённых источников и результата валидации в запись обещания) и `src/core/validate.ts` (новая проверка обещания). Всё остальное в `src/core/*` не меняется.
- Общие поверхности не меняются без координации с exec: `docs/api-contract.md`, `docs/data-model.md`, `src/modules/catalog/**`, `src/modules/knowledge/**`, `src/modules/policy/**`, роутер и `next.config.ts` (маршрут `/promises` реализуется как `src/app/api/promises/route.ts`; если выбран публичный префикс `/v1/promises`, rewrite добавляется в `next.config.ts` только по согласованию с exec), `package.json`, `tsconfig.json`, `vitest.config.ts`.
- Внешние интеграции напоминаний (email, CRM, MAX) не создаются: `reminded_at` остаётся nullable и не заполняется автоматически, а переход в `overdue` считается кодом при чтении журнала и фиксируется в базе.
- Пул тестовых процессов ограничен: `vitest --pool=forks --poolOptions.forks.maxForks=2`.

## Связь критериев приёмки с шагами

| AC | Что проверяет | Шаги |
|---|---|---|
| 1 | Разрешённое подтверждённое обещание записывает диалог, текст, срок, ответственного и статус | 1, 2, 5, 6 |
| 2 | Неизвестный/неутверждённый срок не уходит клиенту; создаётся эскалация | 3, 5, 6 |
| 3 | Журнал менеджера перечисляет открытые, выполненные и просроченные обещания с пометкой «синтетический/демонстрационный» | 4, 5, 6 |
| 4 | Внутренний учёт сроков без внешних интеграций напоминаний | 1, 4, 5, 6 |

## Шаги

### Шаг 1. Миграция: провенанс источника и пометка синтетической записи

- [ ] Создать `db/migrations/6500_promises_provenance.sql` (Up): `ALTER TABLE promises ADD COLUMN source_kind text NULL`, `ADD COLUMN source_id text NULL`, `ADD COLUMN is_synthetic boolean NOT NULL DEFAULT false`; индекс `promises_tenant_due_at_idx ON promises (tenant_id, due_at)` для выборки просроченных. Down: `DROP INDEX IF EXISTS promises_tenant_due_at_idx; ALTER TABLE promises DROP COLUMN IF EXISTS is_synthetic, DROP COLUMN IF EXISTS source_id, DROP COLUMN IF EXISTS source_kind;`. Существующие колонки `due_at`, `owner`, `status` не трогаются — они уже соответствуют AC 1.
- [ ] Применить: `npm run db:migrate:up` → в выводе `применено: 6500_promises_provenance.sql`; затем `docker exec support-agent-pg psql -U postgres -d support_agent -c "\d promises"` — видны `source_kind`, `source_id`, `is_synthetic` и прежние колонки без изменений.
- [ ] Проверить откат: `npm run db:migrate:down` → добавленные колонки исчезают; затем применить миграцию снова.
- [ ] Зафиксировать: внешних интеграций напоминаний нет — `reminded_at` не заполняется ни миграцией, ни кодом среза.

### Шаг 2. Извлечение и запись обещания из подтверждённого источника

- [ ] **Падающий тест** `tests/core/promise-extract.test.ts`: извлечение из ответа модели и списка подтверждённых источников даёт `{ text, dueAt, owner, sourceKind, sourceId }`; обещание без источников (`sources = []`) отклоняется с кодом `no_confirmed_source`; срок, отсутствующий в тексте подтверждённого источника, отклоняется с кодом `deadline_not_in_source`; ответственный по умолчанию — `manager`, но при явном источнике берётся из источника.
- [ ] **Падающий тест** на запись: `recordPromise` сохраняет в `promises` поля `conversation_id`, `text`, `due_at`, `owner`, `status='open'`, `source_kind`, `source_id`, `is_synthetic=false`; запись изолирована по `tenant_id`.
- [ ] Создать `src/core/promise-extract.ts`: публичный API `extractPromise(candidate, sources): PromiseExtraction` с результатом `{ kind: "promise", promise } | { kind: "rejected", reason, detail }`, где `reason` ∈ `no_confirmed_source`, `deadline_not_in_source`, `deadline_unapproved`. Проверка источника обязательна и выполняется кодом: список `sources` должен быть непустым, `sourceKind`/`sourceId` обязаны соответствовать одному из подтверждённых источников, а текст срока и ответственного — находиться в тексте этого источника. Обещание без источника запрещено явным правилом, а не «мягкой» догадкой.
- [ ] Создать `src/modules/promises/index.ts` с публичным API модуля: `recordPromise(input): Promise<PromiseRecord>`, `listPromises(filter): Promise<PromiseRecord[]>`, `markPromiseDone(id): Promise<void>`; типы `PromiseRecord`, `PromiseStatus = "open" | "done" | "overdue"`. Модуль работает только через свой `index.ts`, доступ к `pg` остаётся внутри модуля.
- [ ] В `src/core/run.ts` (узел генерации, после `validateAnswer`) добавить вызов `extractPromise` с уже найденными подтверждёнными источниками: при `kind === "promise"` — запись в `promises`; при `kind === "rejected"` — никаких записей в `promises` и никакого текста обещания в исходящем ответе. Трасса получает узел `promise` с `outcome` и `metadata.sourceKind`.
- [ ] В `src/core/validate.ts` добавить проверку `validatePromise`: запрет цитаты/срока вне источника, запрет сырых ПД в тексте обещания; при нарушении — `valid: false`, и ответ клиенту не отправляется.
- [ ] **Зелёный тест:** `npx vitest run tests/core/promise-extract.test.ts` → все тесты проходят.

### Шаг 3. Неподтверждённый срок → эскалация вместо обещания

- [ ] **Падающий тест** `tests/core/promise-extract.test.ts`: срок, которого нет в подтверждённых источниках, и ответ без источников дают `kind: "rejected"`; в `promises` не появляется ни одной записи; ядро возвращает `outcome: "escalate"` с причиной `no_confirmed_source` и не отправляет клиенту текст обещания.
- [ ] **Падающий тест** на режимы эскалации (ADR-0014): при `ESCALATION_MODE=notice` клиент получает нейтральное уведомление без срока и ответственного; при `ESCALATION_MODE=off` очередь менеджера не создаётся, но обещание в любом случае не отправляется; при `ESCALATION_MODE=on` создаётся запись `escalations` с `reason = "no_confirmed_source"`.
- [ ] Реализовать путь эскалации в `src/core/run.ts`: при отклонённом обещании — `escalationOutcome("no_confirmed_source", …)` и вызов существующей записи эскалации из `src/app/api/chat/route.ts` (`recordEscalation`, таблица `escalations`). Клиенту не отправляется ни срок, ни ответственный, ни формулировка «мы сделаем».
- [ ] **Зелёный тест:** `npx vitest run tests/core/promise-extract.test.ts` → тесты проходят; в базе нет записей `promises` для отклонённого случая.

## На что обратить внимание при проверке

- Таблица `promises` уже существует (миграция 140). Проверяющий должен убедиться, что срез не создаёт таблицу заново и не дублирует `due_at`/`owner`/`status`: их смысл зафиксирован в `docs/data-model.md` §3.5 и соответствует AC 1.
- Ключевой инвариант R11 — обещание допустимо только из подтверждённого источника. Проверка источника выполняется кодом (`extractPromise` + `validatePromise`), а не доверием к формулировке модели: без источника, с источником не из списка подтверждённых или со сроком, которого нет в тексте источника, обещание не создаётся и клиенту не отправляется.
- Отсутствие обещания не должно выглядеть как «мы не можем»: клиент получает нейтральный ответ/уведомление об эскалации без срока и ответственного — в соответствии с ADR-0014 и режимом `ESCALATION_MODE`.
- Просрочка — вычисляемое состояние, а не фоновая задача: внешний планировщик не нужен, `reminded_at` не заполняется, поэтому AC 4 соблюдается по построению.
- Синтетическая пометка — видимая и явная: она не должна прятаться в идентификаторе записи, иначе менеджер примет демо-строку за реальное обязательство.
- Изоляция по `tenant_id` проверяется отдельно: обещание одного диалога не должно попасть в журнал другого арендатора.

# Настройки агента, песочница, история и аудит: план реализации

> **Для исполнителей:** обязательный навык: superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans — выполнять план по задачам. Шаги отмечаются флажком (`- [ ]`).
>
> **Статус: ЧЕРНОВИК — не исполнять до приёма на Г3a и отдельного «поехали» владельца.**

**Цель:** дать менеджеру рабочую поверхность настроек агента (поставщик/модель/endpoint, параметры промпта, лимиты, режим тени) с честным состоянием каждого элемента управления, изолированную песочницу для проверки конфигурации без отправки клиенту, историю тестовых сессий и аудит изменений — в оформлении кабинета по R26.

**Тикет:** `.scratch/support-agent/issues/08-agent-settings-sandbox.md`

**Спецификация:** `.specs/support-agent.md` (копия трекера: `.scratch/support-agent/spec.md`), требования R12 и R26; ADR-0012 (фирменный стиль), ADR-0008 (режим тени), ADR-0016 (однотенантное развёртывание); бриф `docs/HACKATON_BRIEF.md` §8 («Настройки агента (вкладка „Агент“ в админке)»).

**Контракт:** `docs/api-contract.md` §3 (таблица маршрутов: `GET /audit` — «Аудит изменений настроек», приоритет «Тикет настроек»), §1 (модуль наружу отдаёт только публичный `index.ts`), §2 (провенанс: JSON в `snake_case`, ошибки — таблица кодов), §11.1 (кабинет менеджера — тот же барьер доступа и отдельный код менеджера), §12 (секреты не появляются в ответах API, трассе, репозитории и доказательствах).

**Данные:** `docs/data-model.md` §3.1 (`tenants.shadow_mode` — уже существует, `db/migrations/110_tenants.sql`), §3.18 (`agent_steps` — трасса рабочего окружения), §3.19 (`audit_log` — `actor`, `action`, `entity`, `before`, `after`, `created_at`; уже существует, `db/migrations/160_audit.sql`), §6 (диапазон волны 2 — 6000–6999). Новые таблицы среза: `agent_settings`, `agent_dialog_settings`, `agent_test_sessions` (создаются миграцией среза).

**Технологии:** Node.js 22 LTS, Next.js 16 App Router, TypeScript, PostgreSQL 16, `node-pg-migrate`, Vitest. Оформление — CSS custom properties из `src/app/styles/tokens.css` (R26), фирменные цвета в срезе не заводятся.

## Команда проверки

`npm run test -- tests/integration/08-agent-settings-sandbox.test.ts`

Команда собирает модуль настроек, версионирование конфигурации, применение настройки к новому диалогу, изоляцию песочницы, историю тестовых сессий и аудит в один интеграционный прогон.

Номер закрепляет exec: диапазон волны 2 — 6000–6999, по `docs/plans/wave-1-board.md` за настройками агента закреплено 6000 (`agent_settings`). - Новые внешние пути `/settings`, `/settings/sandbox`, `/settings/history` в таблице маршрутов `docs/api-contract.md` §3 не зафиксированы: контракт заморожен, поэтому их регистрация — запрос на ревизию контракта к exec. Срез реализует их под `src/app/api/settings/**` (пути `/api/settings`, `/api/settings/sandbox`, `/api/settings/history`) и сдаёт список путей exec; путь `/audit` используется ровно как в контракте.
- Таблица `audit_log` и колонка `tenants.shadow_mode` уже существуют: срез пишет в них, но не меняет их устройство (`db/migrations/160_audit.sql`, `db/migrations/110_tenants.sql`).
- Секреты (ключ провайдера, токены, пароли) не хранятся в базе, не попадают в аудит, трассу и журналы; в интерфейсе секретные поля только отображаются как заданные окружением и не редактируются.
- Пул тестовых процессов ограничен: `vitest --pool=forks --poolOptions.forks.maxForks=2`. Тяжёлые прогоны (импорт фида, обход сайта) выполняет exec по одному и не совмещаются с прогоном песочницы.

## Связь критериев приёмки с шагами

| AC | Что проверяет | Шаги |
|---|---|---|
| 1 | Менеджер меняет поддерживаемую настройку (`provider`/`model`/`endpoint`, параметры промпта, лимиты, режим тени), и следующий новый диалог использует сохранённую конфигурацию | 1, 2, 7, 8 |
| 2 | Настройка, показанная как доступная, функциональна; неподдерживаемые элементы управления явно отключены и помечены «не реализовано» | 3, 7, 8 |
| 3 | Диалог в песочнице изолирован: нет отправки в веб-чат/MAX, нет изменения клиентского диалога, нет видимых клиенту обещаний, нет влияния на аналитику рабочего окружения | 4, 8 |
| 4 | История хранит конфигурацию/версию, результат/оценку и токены/затраты каждой тестовой сессии | 5, 8 |
| 5 | Аудит пишет субъекта, настройку, время и безопасные значения до/после; секреты открытым текстом не хранятся | 1, 6, 8 |
| 6 | Кабинет менеджера: web-палитра, Montserrat/system, утверждённый логотип, CSS custom properties без хардкода брендовых цветов | 7, 8 |

## Шаги

### Шаг 1. Миграция и хранение конфигурации агента (настройки, версия, аудит)

- [ ] **Падающий тест** `tests/agent-settings/settings.test.ts`: после применения миграции в тестовой базе существуют таблицы `agent_settings`, `agent_dialog_settings`, `agent_test_sessions` с ожидаемыми колонками и ограничениями; изменение настройки создаёт новую версию (`version` растёт на 1, предыдущая строка остаётся в истории), а запись о смене значения появляется в `audit_log` (`actor`, `action`, `entity`, `before`, `after`, `created_at`); две версии одного арендатора не конфликтуют по уникальному индексу `(tenant_id, version)`.
- [ ] Создать `db/migrations/6000_agent_settings.sql` (создаваемый файл):
  - `agent_settings`: `id uuid` PK, `tenant_id uuid NOT NULL`, `version integer NOT NULL`, `provider text NOT NULL`, `model text NOT NULL`, `endpoint text NOT NULL`, `system_prompt text NOT NULL`, `temperature numeric(4,3) NOT NULL`, `max_tokens integer NOT NULL`, `created_by text NOT NULL`, `created_at timestamptz NOT NULL DEFAULT now()`, уникальный индекс `(tenant_id, version)`; версия 1 — стартовая конфигурация, создаётся при первом чтении (`INSERT … ON CONFLICT DO NOTHING` по `tenant_id`, `version = 1`) из значений окружения и стандартного промпта ядра;
  - в таблице лежат только те настройки, у которых есть работающий потребитель: `provider`/`model`/`endpoint`/`temperature`/`max_tokens` читает клиент модели, `system_prompt` — ядро. Колонок `tools`, `skills`, `mcp` и `limits` здесь нет намеренно: переключатели инструментов ядро не проверяет (поиск по БЗ, каталог и policy вызываются всегда), навыки и MCP не реализованы, лимиты задаются окружением и общим модулем `src/modules/limits`. Хранить такие значения в конфигурации — значило бы завести поле без потребителя, то есть ровно тот случай, который AC 2 запрещает. Их состояние живёт в реестре возможностей (шаг 3), а не в базе;
  - колонки `shadow_mode` в `agent_settings` нет намеренно: режим тени уже живёт в `tenants.shadow_mode` (`db/migrations/110_tenants.sql`), и тикет 06 (`docs/plans/06-shadow-mode.md`) объявляет его единственным источником истины. Срез 08 не заводит второе место хранения и не дублирует значение; переключатель режима тени в кабинете пишет в `tenants.shadow_mode` через сервис среза 06.
  - `agent_dialog_settings`: `conversation_id uuid` PK → `conversations(id)` `ON DELETE CASCADE`, `tenant_id uuid NOT NULL`, `version integer NOT NULL`, `created_at timestamptz NOT NULL DEFAULT now()` — привязка версии конфигурации к диалогу: изменение настройки применяется к следующему **новому** диалогу, а текущий диалог продолжает работать на своей версии;
  - `agent_test_sessions`: `id uuid` PK, `tenant_id uuid NOT NULL`, `settings_version integer NOT NULL`, `settings_snapshot jsonb NOT NULL`, `request_text_masked text NOT NULL`, `result jsonb NOT NULL`, `tokens_in integer NOT NULL DEFAULT 0`, `tokens_out integer NOT NULL DEFAULT 0`, `cost_rub numeric(12,4) NOT NULL DEFAULT 0`, `actor text NOT NULL`, `created_at timestamptz NOT NULL DEFAULT now()`, индекс `(tenant_id, created_at DESC)`;
  - секция `-- Down Migration`: `DROP TABLE agent_test_sessions; DROP TABLE agent_dialog_settings; DROP TABLE agent_settings;` — откат не трогает `audit_log` и `tenants`, потому что их устройство срез не менял.
- [ ] Применить: `npm run db:migrate:up` → в выводе `применено: 6000_agent_settings.sql`. Проверить откат: `npm run db:migrate:down` → три таблицы исчезают, `audit_log` и `tenants` на месте; затем применить снова.
- [ ] Реализовать `src/modules/agent-settings/store.ts` (создаваемый файл): `readCurrentSettings(tenantId): Promise<AgentSettings>`, `updateSetting(tenantId, key, value, actor): Promise<AgentSettings>`, `bindDialogVersion(tenantId, conversationId): Promise<number>`, `listVersions(tenantId): Promise<AgentSettings[]>`. `updateSetting` в одной транзакции читает текущую версию, создаёт следующую и пишет запись аудита; значение секретного поля (`api_key`, `token`, `secret`, `password`, `authorization`) отклоняется с ошибкой — такие поля в конфигурации не хранятся; ключ `shadow_mode` в `updateSetting` не принимается — режим тени меняется в `tenants.shadow_mode` (см. тикет 06), и его изменение тоже пишется в `audit_log`, но отдельным сервисом.
- [ ] Реализовать `src/modules/agent-settings/index.ts` (создаваемый файл) — публичный API модуля: наружу отдаются только `readCurrentSettings`, `updateSetting`, `bindDialogVersion`, `listVersions`, `describeCapabilities`, `runSandbox`, `listTestSessions`, `listAuditEntries`, `redactSecrets`. Внутренние файлы напрямую не импортируются (правило `docs/api-contract.md` §1).
- [ ] **Зелёный тест:** `npm run test -- tests/agent-settings/settings.test.ts` — версия растёт, история версий читается, аудит получает запись, откат и повторное применение миграции проходят.

### Шаг 2. Падающий тест: менеджер меняет настройку — следующий новый диалог использует сохранённую конфигурацию

- [ ] **Падающий тест** `tests/agent-settings/settings.test.ts` (второй блок): менеджер сохраняет поддерживаемую настройку (`model` и `endpoint`, затем `temperature`/`max_tokens`); следующий новый диалог (`conversation_id` которого ранее не встречался) вызывает модель с сохранёнными значениями — в подставном `fetch` видны адрес `endpoint`, идентификатор `model`, `temperature` и `max_tokens`; диалог, начатый **до** изменения, продолжает работать на прежней версии (привязка версии к диалогу); ключ провайдера берётся только из окружения и в запрос/аудит/трассу не попадает.
- [ ] Реализовать в `src/core/model.ts` (явно оговорённое изменение): публичная функция `createModelClientForSettings(settings: { provider: string; model: string; endpoint: string; temperature: number; maxTokens: number }): ModelClient` — адрес и модель берутся из конфигурации, ключ — из окружения (`OPENCODE_API_KEY`), значения по умолчанию окружения используются только для настроек, которые ещё не заданы менеджером; поддерживаются те же лимиты и повтор после 429, что сейчас.
- [ ] Реализовать в `src/core/run.ts` (явно оговорённое изменение): в начале `runAgent` конфигурация читается один раз (`readCurrentSettings` + `bindDialogVersion`), системный промпт берётся из сохранённого `system_prompt` (значение по умолчанию — нынешняя константа `SYSTEM_PROMPT`, вынесенная в публичную функцию `defaultSystemPrompt()`), а модель вызывается через клиент, собранный по сохранённой конфигурации; порядок узлов, таймауты, формат `AgentOutcome` и запись трассы не меняются.
- [ ] **Зелёный тест:** `npm run test -- tests/agent-settings/settings.test.ts` — новый диалог использует сохранённую конфигурацию, старый диалог — свою версию, секрет не утёк.

### Шаг 3. Падающий тест: неподдерживаемый элемент управления отображается отключённым

- [ ] **Падающий тест** `tests/agent-settings/capabilities.test.ts`: реестр возможностей возвращает для каждого элемента управления признак `supported` и, при `supported: false`, причину с пометкой «не реализовано»; в репозитории нет ни MCP-клиента, ни загрузчика markdown-навыков, ни интеграций email/CRM — значит элементы `mcp` (подключения к внешним серверам: Streamable HTTP / SSE / stdio), `skills` (markdown-навыки) и `promises.schedule` обязаны быть `supported: false` с причиной; параметры `top_p` и `seed` — `supported: false`, потому что клиент модели их не передаёт; переключатели инструментов (`tools`) — `supported: false` с причиной «ядро вызывает поиск по БЗ, каталог и проверку полномочий всегда; отключение отдельного инструмента не реализовано», потому что так их и устроено (`src/core/run.ts` не проверяет флаги инструментов); `limits` — `supported: false` с причиной «лимиты задаются переменными окружения и общим модулем `src/modules/limits`», потому что из кабинета они не меняются; поддерживаемыми остаются `provider`, `model`, `endpoint`, `system_prompt`, `temperature`, `max_tokens` и `shadow_mode` (режим тени поддерживается, но живёт в `tenants.shadow_mode`); элемент управления с `supported: false` нельзя изменить — попытка изменения возвращает ошибку, а не «успешное» сохранение.
- [ ] Реализовать `src/modules/agent-settings/capabilities.ts` (создаваемый файл): `describeCapabilities(): CapabilityDescriptor[]`, где `CapabilityDescriptor = { key: string; label: string; supported: boolean; reason: string | null; control: "toggle" | "text" | "number" | "select" }`. Причина для неподдерживаемого элемента — человекочитаемый текст с пометкой «не реализовано» (например: «MCP-подключения к внешним серверам не реализованы: в проекте нет MCP-клиента»), а не пустая строка и не тихий игнор. Реестр — единственное место, где перечислено состояние каждого элемента управления: страница кабинета и маршрут `GET /api/settings` берут её отсюда, поэтому «отключено в интерфейсе» и «отключено в API» не могут разойтись.
- [ ] **Зелёный тест:** `npm run test -- tests/agent-settings/capabilities.test.ts` — неподдерживаемые элементы помечены и не принимают изменений, поддерживаемые принимают.

### Шаг 4. Падающий тест: диалог в песочнице изолирован

- [ ] **Падающий тест** `tests/agent-settings/sandbox.test.ts`: до запуска песочницы фиксируются счётчики строк в `messages`, `conversations`, `escalations`, `promises`, `agent_steps`, `usage_counters`; после тестовой сессии в песочнице все счётчики равны прежним — песочница не пишет в рабочие таблицы и не влияет на аналитику рабочего окружения; в подставленном `fetch` нет обращений к `platform-api.max.ru` и нет запроса к веб-чату (`/v1/chat`), а в исходящем тексте нет формулировок-обещаний клиенту (нет записи в `promises` и нет видимых клиенту обещаний в ответе); тестовая сессия получает собственный идентификатор и собственную трассу, не связанную с `agent_steps`.
- [ ] Реализовать `src/modules/agent-settings/sandbox.ts` (создаваемый файл): `runSandbox(input: { tenantId: string; actor: string; text: string; settingsVersion?: number }): Promise<SandboxResult>`. Песочница не вызывает `runAgent` (`src/core/run.ts`) и не пишет в `agent_steps`/`messages`/`conversations`/`escalations`/`promises`: она собирает собственный изолированный проход — маскирование входа через публичный `maskPersonalData` (`src/core/mask.ts`), поиск источников через публичный `search` (`src/modules/knowledge/index.ts`), вызов модели по сохранённой конфигурации через клиент из `src/core/model.ts`, проверка ответа через `validateAnswer` (`src/core/validate.ts`); результат возвращается и пишется только в `agent_test_sessions`. Внешние каналы (веб-чат, MAX) песочница не вызывает вовсе, а результат не возвращается клиентскому интерфейсу и не создаёт обещаний. Клиент модели песочница собирает так же, как ядро для нового диалога (`createModelClientForSettings` по сохранённой конфигурации, шаг 2) — иначе проверялась бы не та конфигурация, которую менеджер настроил.

## На что обратить внимание при проверке

- Честность состояния важнее полноты формы: элемент управления, который не работает, обязан быть отключён и подписан «не реализовано». В проекте не реализованы внешние интеграции (email/CRM), MCP-подключения к внешним серверам и markdown-навыки; переключатели отдельных инструментов ядро тоже не проверяет, а лимиты задаются окружением. Всё это показывается отключённым — показывать рабочим нельзя.
- Обратная сторона той же честности: в конфигурации не заводятся поля под нереализованные настройки. Хранить `skills`/`mcp`/`limits` в таблице без работающего потребителя — значило бы создать видимость настройки, которой нет.
- Ключ провайдера не хранится в конфигурации и не редактируется в кабинете: он задаётся переменной окружения. Попытка записать секретное поле отклоняется, а не «сохраняется в открытом виде».
- Изменение настройки действует на следующий новый диалог: уже открытый диалог продолжает работать на той версии, с которой начался. Это проверяется двумя разными `conversation_id` в одном тесте.
- Песочница не проходит через `runAgent` намеренно: ядро пишет трассу в `agent_steps`, а аналитика тикета 09 считается по этой таблице. Проверка изоляции — это проверка того, что рабочие таблицы и счётчики не изменились, а не проверка отсутствия логов.
- Песочница не создаёт обещаний и не возвращает клиентский текст: её результат виден только менеджеру в истории.
- Аудит читается по арендатору и содержит значения до/после; секретные поля заменены маской, а не исходной строкой. Проверяется и содержимое `before`/`after`, и отсутствие секрета в `agent_steps`, `agent_test_sessions` и ответе песочницы.
- Токены и затраты в истории берутся из фактического ответа модели (`tokensIn`/`tokensOut`/`costRub` из `ModelResult`), а не из заранее заданных чисел. В тесте подставляется клиент модели с известной метрикой, поэтому ненулевые значения проверяемы; с настоящей заглушкой `stubModelClient` значения будут нулевыми — это нормально и означает лишь, что модель не вызывалась.
- Страница кабинета использует только переменные из `src/app/styles/tokens.css`: файл токенов — общая поверхность exec, свои hex в срезе не заводятся. Проверка логотипа — побайтовое совпадение с файлом из `docs/лого софтлайн/`, охранное поле не меньше высоты.
- Маршруты `/settings`, `/settings/sandbox`, `/settings/history` в замороженной таблице `docs/api-contract.md` §3 не зафиксированы; их регистрация — запрос на ревизию контракта к exec. `/audit` используется ровно как в контракте, без изменения `next.config.ts`.

# ИИ-агент поддержки — полный бриф проекта

> Хакатон «ИИкузница», трек «Клиентские сценарии». Заказчик — B2B-магазин ПО. Спринт: 26.11 19:00 → 28.11 19:00 (Камчатка). Документ собран 26.11.2026.

## 1. Проблема

Поддержка тратит 15–30 минут на диалог при потоке 1000–2000 обращений в месяц. Вопросы повторяются: продукты, наличие, сроки, условия. КП и счета собирают вручную. Числа — ориентиры из брифа, в описании продукта помечать как допущение, лучше заменить своими по трассам после демо.

## 2. Что должен делать агент

- Отвечать на типовые вопросы в чате
- Консультировать по продуктам, условиям, срокам, особым условиям
- Формировать КП автоматически (по запросу и каталогу)
- Формировать счёт автоматически
- Передавать сложные случаи менеджеру (эскалация)
- Вести журнал действий (трасса шагов)
- Пополнять базу знаний

## 3. Два клиентских входа

1. **Веб-виджет чата** на сайте магазина — виджет открывается на любой странице, клиент пишет, получает ответ. Узнавание клиента — подписанная cookie с id диалога (по IP намеренно не узнаём: за одним офисным адресом двадцать человек).
2. **Бот в MAX** — мессенджер, клиента узнаёт сам по себе. Веб-версия MAX в браузере разрешена организаторами, телефон не нужен. Телефон и почту можно имитировать.

Два раздела одного приложения: клиентский чат и кабинет менеджера. Полноценный ручной чат менеджера не обязателен.

## 4. Каналы и адаптеры

- Каналы — адаптеры `web` и `max` с одним интерфейсом «принять сообщение / отправить ответ».
- Ядро — агентный цикл из 7 узлов, про каналы и интерфейсы не знает.
- Telegram не подключаем: его нет в дереве, а не «вырезаем из готового».

## 5. Архитектура

**Один процесс с модулями, не микросервисы.** За 48 часов шесть сервисов съедят полдня на конфигурацию.

Модули (границы — импорт только через `index.ts`):
- `catalog` — товары, цены, лицензии, правила скидок
- `knowledge` — статьи, куски документов, поиск по смыслу, индексация
- `documents` — КП и счёт из шаблонов, PDF
- `policy` — полномочия: что решается само, что уходит человеку
- `promises` — обещания клиенту, дедлайны, напоминания
- `telemetry` — трассы шагов, токены, стоимость диалога

**Ядро** — агентный цикл из 7 узлов.

## 6. Агентность

- Один агент, без мультиагентной схемы (дороже, медленнее, менее предсказуемы на демо)
- Одна модель на всё: классификация — тот же вызов с коротким промптом
- Валидатор заменяет «второго агента» кодом: сверяет цифры с каталогом, цитаты с текстом статьи
- **Суммы считает только код** — модель физически не может придумать цену
- Таймауты: LLM-вызов 120 с (до первого токена бывает минута), внутренние шаги 5 с, потолок диалога 5 мин; при 429 — один ретрай через 30 с

## 7. Экраны и интерфейсы

### Клиентский чат (веб-виджет)
- Живой чат: вопрос клиента → шаги ответа (поиск, каталог, расчёт) → ответ
- Стоимость диалога в реальном времени (~токены, ~рубли)
- При эскалации: «передал менеджеру, ответим в течение часа»

### Кабинет менеджера (админка)
- **Очередь** — обращения, требующие человека: короткое резюме, готовый черновик ответа, «что сделала программа», «сколько стоило», «что пообещала»
- **Обещания** — журнал: что пообещали, кому, когда, статус
- **Знания и данные** — статьи, документы, шаблоны, таблицы данных, индексация
- **Агент** — настройки агента (см. раздел 8)
- **Аналитика** — автозакрытие %, стоимость запроса, экономия времени, пробелы базы знаний
- **Архитектура** — схема решения для показа
- **Режим тени** — тумблер в шапке

### Настройки агента (вкладка «Агент» в админке)
- Подключение к модели: OpenCode Go (подписка) + DeepSeek (основная), custom endpoint (запасной)
- Инструменты с тумблерами: knowledge.search, catalog.get, documents.render, policy.check, promises.schedule
- Скиллы (markdown-навыки, добавление .md)
- MCP-подключения: Streamable HTTP / SSE / stdio, проверка подключения
- Системный промпт (редактор, сброс к стандартному)
- Параметры модели: температура, top_p, максимум токенов, seed
- Лимиты и безопасность: таймауты, порог эскалации скидки, режим тени, маскировка ПД (не отключается)
- **Песочница** — тестовый чат с агентом без отправки реальному клиенту
- **История тестирования** — каждая сессия с конфигом (модель, температура, скиллы, MCP, тень), оценка ответа, стоимость, кнопка «Повторить»
- Аудит изменений: кто, что, когда

## 8. Фишки сверх функционала

1. **Режим тени** — тумблер: агент отвечает сам или готовит черновик в очередь менеджеру. Снимает главный страх заказчика «а вдруг ИИ наобещает». Постепенное делегирование: первая неделя всё проверяет человек, потом типовое уходит в авто.
2. **Валидатор цифр** — перед отправкой каждая сумма сверяется с каталогом, каждая цитата — с текстом статьи. Не совпало — не отправляем.
3. **Экономика из своих логов** — стоимость каждого ответа считается по шагам автоматически (токены × цена), не пишется от руки в презентации.
4. **Журнал обещаний** — что агент пообещал клиенту, дедлайны, напоминания. Если агент пообещал — это зафиксировано и контролируется.
5. **Песочница + история тестов** — менеджер проверяет изменения настроек на тестовых вопросах и видит, при какой конфигурации агент отвечал точнее и дешевле.
6. **Экран настроек агента** — отвечает на вопросы жюри: «как вы управляете агентом», «можно ли настроить без программиста», «где видно, что делал оператор».

## 9. Данные и документы

- Postgres 16 + pgvector, одна база: каталог, база знаний, диалоги, документы, обещания, трассы
- PDF собирается на сервере (одинаково выглядит на записи и у жюри)
- Состояние диалога в базе — переживает деплой и перезапуск
- Индексация документов — фоновая задача, на демо не запускается
- Шаблоны КП и счёта придумываем сами (заказчик не даёт): КП с условиями (скидка, оплата 50/50, срок поставки, гарантия), счёт с реквизитами и сроками оплаты

## 10. Персональные данные — три барьера

1. Маскировщик на входе: телефоны, почта, ИНН, счета → метки; таблица соответствий в модель не уходит
2. Модель физически не видит реквизиты: отдаёт структуру, имя и счёт подставляет код после
3. Проверка на выходе: метки восстанавливаются у нас перед отправкой клиенту

## 11. Многопользовательность

- Мультитенантность как система — не делаем; tenant_id — делаем с первого дня (колонка во всех таблицах, подстановка из сессии одной точкой)
- Три магазина на одной установке выдержит
- Одновременные пользователи: каждый диалог — отдельный запрос, состояние в базе, пул соединений
- Предел ~10 одновременных ходов, остальные в очереди с честным ожиданием
- Блокировка на диалог: второй ход в тот же диалог ждёт первый

## 12. Стек

Next.js + shadcn (два интерфейса), FastAPI или Node (API), Postgres 16 + pgvector, OpenCode Go + DeepSeek (LLM), документы из шаблонов, PDF на сервере.

Стенд: 4 vCPU / 8 ГБ / 80 ГБ, Dokploy + Traefik, домен aisupport.dzenesis.ru.

## 13. Что сознательно не делаем

Отдельные сервисы и очередь задач. Мультиагентную схему. Полноценную мультитенантность с лимитами и биллингом. Telegram. Телефонию и почту (имитация разрешена). Локальные эмбеддинги.

## 14. Что забираем из системы Ивы

Репозиторий: https://github.com/iva-agent (публичные компоненты)

- **Схема подключения провайдеров** — карточка «Подключение»: тип (API-ключ / OpenAI OAuth / Claude CLI / OpenCode Go / custom), Base URL, ключ, модель, «Проверить подключение»
- **Система скиллов** — markdown-навыки с триггером, подгружаются по триггеру, а не висят в промпте всегда
- **MCP-интеграции** — Model Context Protocol: Streamable HTTP / SSE / stdio, сервер объявляет свои инструменты
- **Валидатор ответов** — сверка фактов с источниками перед отправкой
- **Трасса шагов (telemetry)** — каждый шаг агента логируется с токенами и стоимостью
- **Режим аудита** — кто, что, когда менял в настройках

## 15. Правила и сроки

- Код прототипа — только со старта спринта (26.11 19:00 по Камчатке)
- Демо-видео до 3 минут, одним дублем, без монтажа
- Описание продукта до 1 страницы: подход, стек, функциональность, стоимость эксплуатации и внедрения
- Оценка: 0–3 по соответствию, убедительности демо, полноте описания (макс 9 на отборе, 18 на финале)
- Порог 9/18 — иначе победителя нет; 12/18 — «Путь к витрине»
- Жюри может запросить исходный код и демо в реальном времени
- Стенд живёт 28.11 10:00 МСК → 3.12 23:59

## 16. Доступ и безопасность стенда

- Код-гейт на входе: страница «Введите код стенда» → cookie. Жюри получает код в описании
- Rate limit: 10 запросов/мин с IP, лимит 50 диалогов/день
- Демо-ключ API модели с жёстким лимитом бюджета
- UFW: только 22/80/443; fail2ban на SSH; Docker API не открыт наружу

Разработка через дом: от спеки до приёмки

Профиль dev-pipeline, три раздельные launcher-команды, проверки ролей и журнал целевой фичи .house/work/<task>/pipeline.json и violations.md
spec: домен и спека exec: код в изоляции supervisor: приёмка, фронтир, переходы дом: транспорт проверка по правилам supervisor, машинной блокировки нет

1. Три окна, три роли

Окно SPEC omp-сессия

профиль dev-pipeline, запуск launch-spec из корня проекта
  • прожарка требований, глоссарий, ADR, спеки, граф тикетов
  • скиллы: setup-matt-pocock-skills, triage, grill-with-docs, grill-me, grilling, domain-modeling, codebase-design, to-spec, to-tickets
  • triage: постоянный разбор входящих issue и PR в брифы; разово только настройка меток
  • пишет только артефакты домена: GLOSSARY.md, .specs/, adr/, граф
  • implement-spec не поставлен: он тянет исполнение с tdd и ревью Мэтта

Окно EXEC omp-сессия

профиль dev-pipeline, запуск launch-exec из корня проекта
  • реализация тикетов в worktree, микро-планы, TDD, отладка
  • скиллы: using-superpowers, using-git-worktrees, writing-plans, executing-plans, subagent-driven-development, test-driven-development, systematic-debugging, verification-before-completion, diagnosing-bugs
  • читает домен (RO), пишет только код, тесты, docs/superpowers/plans/

Окно SUPERVISOR omp-сессия

профиль dev-pipeline, запуск launch-supervisor из корня проекта
  • приёмка Г1, Г2, Г3a, Г3b и Г4; журнал решений и evidence ведётся в pipeline.json целевой фичи
  • скиллы: supervisor-pipeline, collaborative-work, gates-first, quality-assurance, requirements-engineering, verification-before-completion, requesting-code-review, finishing-a-development-branch, code-review, improve-codebase-architecture, pr, retro, codebase-design, grilling, domain-modeling, writing-for-agents
  • improve-codebase-architecture и retro вызываются по триггерам после Г3b/Г4, read-only; находки уходят в spec или pipeline.json, не в violations.md
  • сообщения House доставляются от имени отправителя; ACK и DONE не заменяют приёмку
  • фронтир пересчитывается только после принятого тикета и проверки актуальных блокеров

HOUSE: только канал доставки, не система приёмки

Каталог .house это транспорт, а work/ внутри него это журнал процесса; прежний каталог журнала удалён, искать его не нужно.

переписка.mdканал сообщений и доставки: ACK / DONE не равны ACCEPTED
.house/work/<task>/pipeline.jsonжурнал гейтов одной фичи: решения, входы, revisions, evidence, замечания и frontier; пишет supervisor
.house/work/<task>/violations.mdжурнал нарушений, влияния, ответственных и статуса исправления
state.jsonтранспортные отметки доставки, к приёмке не относится

2. Три фазы разработки и пять гейтов приёмки

Фаза 1 · Г1

Домен и спека

владелец: SPEC
  1. Шаг 0: подготовка каталога — изолировать рабочую область: git init в каталоге проекта и копия AGENTS.md. Без изоляции корнем станет родительский репозиторий
  2. setup-matt-pocock-skills: настройка трекера и меток (разово, при первом подключении)
  3. triage: входящие issue/PR → категория и бриф (постоянно)
  4. grill-with-docs или grill-me: допрос по развилкам требований
  5. domain-modeling: GLOSSARY.md и docs/adr/ — термины и решения
  6. codebase-design + to-spec: спеку публикуют в трекере + локальная копия .specs/<name>.md
Г1: обе копии спеки синхронны; решение ACCEPTED / CHANGES_REQUESTED записывается в pipeline.json супервизором через skill://supervisor-pipeline
Фаза 1 · Г2

Декомпозиция

владелец: SPEC
  1. to-tickets: спека → граф тикетов с блокирующими рёбрами и критериями приёмки
  2. фронтир: тикеты с нулём активных блокеров
  3. Супервизор проверяет матрицу требование → тикет → AC в обе стороны
Г2: граф валиден; frontier выдан exec; решение записывается в pipeline.json супервизором через skill://supervisor-pipeline
Фаза 2 · Г3a

Код в изоляции

владелец: EXEC
  1. using-superpowers: bootstrap тикета
  2. using-git-worktrees: .worktrees/<ticket>/
  3. writing-plans: план Superpowers на один тикет
  4. subagent-driven-development + test-driven-development: код по TDD (первый тест падает)
  5. systematic-debugging: отладка и диагностика при необходимости
  6. verification-before-completion: свежий прогон проверок с exit code перед сдачей DONE
Г3a: план принят супервизором; «поехали» владельца отдельно; код разблокирован
Фаза 2 · Г3b

Проверка сдачи тикета

проверяет: SUPERVISOR
  1. Exec сдаёт `DONE` со ссылкой на план, diff и результаты проверок
  2. Супервизор сверяет diff с планом, тикетом и критериями спеки
  3. Проверки Spec и Standards — отдельные оси; замечания адресуются spec или exec
Г3b: ACCEPTED/CHANGES_REQUESTED записываются в pipeline.json супервизором через skill://supervisor-pipeline; frontier пересчитывается
Фаза 3 · Г4

Ревью и интеграция

владелец: SUPERVISOR
  1. requesting-code-review → finishing-a-development-branch
  2. code-review: отдельные оси Spec / Standards
  3. pr: интеграция после ACCEPTED; merge по разрешению владельца
  4. improve-codebase-architecture (read-only): архитектурный скан в Г4
  5. retro (с writing-for-agents): ретроспектива по итогам сессии
Г4: каждое требование покрыто принятым тикетом; слияние по разрешению владельца

3. Матрица файлов: кто что пишет (правила ролей)

Связка форматов Matt Pocock и Superpowers: to-spec публикует спеку в трекер; локальная .specs/<name>.md копия обязательна и синхронизируется с ней до Г1. to-tickets строит связанные задачи; план Superpowers отдельный и относится ровно к одному тикету.

  • .specs/<name>.md и GLOSSARY/ADR: контракт, только чтение для exec.
  • Тикет: один ID, блокирующие рёбра в трекере или .scratch/. ID входит в имя плана, ветки и worktree.
  • docs/superpowers/plans/: план Superpowers на один тикет, временный исполнительский формат.
  • .superpowers/sdd/: отдельный git-ignored журнал SDD, briefs и отчётов.
  • В шапке плана: Spec: со ссылкой на .specs/<name>.md и Global Constraints, дословно из спеки.
  • Уровень спеки: пользовательское поведение и решения, без конкретных путей к файлам.
  • Уровень плана: точные файлы, интерфейсы и команды проверок для одного тикета.
  • to-tickets делит фичу на вертикальные тикеты; план Superpowers делит тикет на микро-шаги.

Исполнитель читает спеку, тикет и план вместе. Трекерная и локальная копии сверяются до Г1; их рассинхронизация блокирует приёмку.

Одна строка = один путь; R/W разрешён, RO только чтение, «запрет» это правило роли, машинной блокировки пока нет.

4. Что включено сейчас, а что ещё нет

Работает уже сейчас

  • один профиль dev-pipeline, разрешённые скиллы профиля заданы через includeSkills; каждый launcher отдельно ограничивает навыки роли через --skills
  • глобальные слои выключены; нужные supervisor навыки подключены адресно, случайные пользовательские скиллы не подмешиваются
  • три команды из PATH: launch-spec, launch-exec, launch-supervisor, каждая со своим списком --skills
  • AGENTS.md и supervisor-pipeline задают проверки; pipeline.json целевой фичи хранит решения и evidence, supervisor ведёт его по общей схеме

Ролевое сужение: статус

  • проверен профильный список скиллов launcher-ов; --skills supervisor запускает только явно названный набор
  • includeSkills общий для профиля, а CLI-утилиты omp не проверяют модельный каталог
  • явный skill:// может обойти скрытие, поэтому это остаётся задачей будущего аудитора

Аудитор и системный гейт ещё не построены

  • роль supervisor получает пошаговый скилл supervisor-pipeline плюс code-review и QA навыки
  • каждый переход требует проверяемых доказательств; при пробеле переход отклоняется, исправление адресуется spec или exec
  • это жёсткое требование процесса, а не машинная блокировка инструментов; профильный аудитор не создан
  • совмещение ролей в одном окне допустимо только с записью в violations.md

Что не подделать и без гейта

  • pipeline.json: пишет supervisor, spec/exec туда не лезут по правилам
  • worktree и ветки: git-история показывает, кто и когда писал
  • тесты: зелёный прогон это артефакт, его видно
  • frontier пересчитывается только после ACCEPTED тикета и с учётом актуальных зависимостей

Quality-gates выполняет модель supervisor по скиллу и сохраняет evidence. Машинной блокировки и отдельного аудитора пока нет.

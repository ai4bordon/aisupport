# 14 — Сценарии подбора продукта через каталог

Status: open
Blocked by: замороженный контракт (`docs/api-contract.md`, `docs/data-model.md`), не тикет 01
Type: task
Priority: P0
Spec: `.specs/support-agent.md` requirements R1a, R1b; ADR-0010, ADR-0015
Plan: `docs/plans/14-product-selection-catalog.md` (требует Г3a и отдельного «поехали»)

## Цель

Подключить каталог к ядру и реализовать оба уже принятых сценария R1a/R1b: подбор по названию известного продукта с уточнением недостающих слотов и рекомендацию вариантов, когда клиент не знает продукт. Это отдельная работа по зафиксированному P0-дефекту ADR-0015; критерии тикета 01 не изменяются.

## Границы

- Сценарии выполняются через общее ядро, независимо от канала Web/MAX; каталог вызывается через публичный API модуля `catalog`.
- Для известного продукта использовать структурный поиск каталога и его карточки; цены/версии брать из датированного снимка, не представлять как актуальное подтверждение.
- Недостающие слоты состояния обращения: количество пользователей/лицензий, срок лицензии, тип развёртывания. Задавать по одному вопросу за ход; после сбора обязательных данных показать подходящий результат, не заполняя неизвестное предположением.
- Для подбора без названия продукта выяснить задачу, число пользователей, бюджет и инфраструктуру; если сведений недостаточно, задавать уточнения по одному. Обосновывать рекомендации только сведениями каталога и опубликованными источниками, включая предоставленные материалы Store и БЗ. Полномочия, безопасные ответы, маскирование ПД и правила эскалации остаются действующими.
- Состояние слотов должно переживать отдельные сообщения только в том же диалоге.
- Не менять общий контракт, модель данных или чужие миграционные диапазоны без координации exec; хранение состояния и файлы реализации определить в плане.

## Критерии приёмки

1. **Известный продукт, все параметры заданы:** обращение с названием продукта и количеством, сроком лицензии и типом развёртывания вызывает поиск каталога, возвращает подходящую версию/редакцию, цену из датированного снимка и ссылку на карточку источника.
2. **Известный продукт, не хватает параметра:** обращение с названием продукта, но без количества, задаёт один уточняющий вопрос о количестве, не рекомендует вариант преждевременно и сохраняет известный продукт и уже собранные слоты для следующего сообщения. Аналогично обрабатываются отсутствующие срок лицензии или тип развёртывания.
3. **Неизвестный продукт:** выяснить задачу, число пользователей, бюджет и инфраструктуру; если данных не хватает, задать уточнения по одному, а затем при достаточных основаниях вернуть 2–3 различимых варианта из каталога с кратким обоснованием и ссылкой на карточку/опубликованный источник каждого варианта.
4. Цена, версии, лицензирование и наличие подтверждаются карточкой/датированным каталогом; числовые и коммерческие условия не придумываются. Недостаточные данные или неоднозначное совпадение не выдаются за точный результат.
5. Последующие сообщения с тем же `conversation id` продолжают сбор слотов; состояние слотов других диалогов не подмешивается.
6. Регрессионные тесты покрывают три основные ветки: известный продукт с полными данными → карточка и цена; известный продукт без количества → уточняющий вопрос и сохранение состояния; неизвестный продукт → подбор 2–3 вариантов с обоснованием и ссылками.
7. Сценарии проверяются через общий API ядра с синтетическими входами и фикстурами каталога; тесты подтверждают использование каталога, а не только поиска по БЗ. Живой прогон обоих сценариев фиксируется отдельно, без секретов и реальных персональных данных.

## Команда проверки

Exec указывает целевую команду после выбора тестового seam в плане Г3a.

## Свидетельства

Сохранить тестовый вывод и примеры трёх принятых веток: найденная карточка с ценой/ссылкой, уточняющий вопрос с продолжением того же диалога, 2–3 рекомендации с обоснованием. Включить подтверждение вызова каталога и живого веб-сценария; не включать секреты или исходные персональные данные.

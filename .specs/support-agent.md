 # Спецификация: ИИ-агент поддержки

 ## Статус и источники

 Спецификация для прототипа хакатона «ИИкузница», трек «Клиентские сценарии».

 Источники: `docs/ИИ_агент_поддержки.md` (требования задачи), `docs/ИИ-агент поддержки_QA.md` (ответы заказчика), `docs/HACKATON_BRIEF.md` (бриф проекта), «Положение о проведении конкурса» §§ 4.4–4.8 и Приложение 1. Текущие решения владельца переданы через supervisor/exec в `.house/переписка.md`: MAX обязателен; персональные данные маскируются расширенным составом; документы БЗ и черновики статей проходят отдельные потоки одобрения; для MAX в спринте используется Long Polling; до старта спринта разрешены только анализ и проектирование, а реализация выполняется по тикетам после Г3a.

 Локальный трекер задач — файлы Markdown в `.scratch/support-agent/`. Копия спецификации для трекера: `.scratch/support-agent/spec.md`.

 ### Приоритет требований

 1. Положение и опубликованные требования задачи/ответы на вопросы.
 2. Явные решения владельца, записанные в журнале проекта.
 3. Бриф — намерения по архитектуре и допущения, если они не противоречат более приоритетным источникам.
 4. Страницы и репозиторий Ивы — только источники идей и образцы пользовательского интерфейса, но не продуктовые решения.

 ## Цель

 Сократить ручную работу поддержки B2B-магазина ПО: отвечать на вопросы по проверенным источникам, подбирать товар, рассчитывать суммы, формировать КП и счёт, передавать нерешённые случаи менеджеру и пополнять проверяемую базу знаний.

 Числа 15–30 минут на диалог, 1000–2000 обращений в месяц, доли повторных обращений и потерянных обращений — ориентиры из исходного брифа, а не результаты измерений продукта. При использовании в описании продукта их нужно обозначать как исходные ориентиры/допущения; показатели пилота вычислять по трассам.

 ## Область продукта

 ### Обязательный объём

 - Web и MAX подключены к общему ядру; агент отвечает по опубликованной БЗ и каталогу.
 - По явному запросу клиента система автоматически формирует КП при наличии цены в каталоге; предварительное одобрение менеджера не требуется. Счёт автоматически формируется только по отдельному явному запросу. Суммы и реквизиты задаёт код.
 - Скидка без купона до 5% включительно разрешена и рассчитывается кодом; запрос большей скидки, отсрочки, возврат и другие неподтверждённые условия эскалируются (ADR-0019).
 - Факт о товаре проверяется по порядку «опубликованная БЗ → явно заполненное поле карточки каталога с тем же `offer_id` → эскалация». При проблеме после покупки сначала предлагается применимая инструкция опубликованной справки; если инструкции нет или она не помогла — эскалация.
 - Кабинет предоставляет два разных потока знаний: пользовательские документы и агентские черновики требуют одобрения; разрешённый ответ менеджера, сохранённый действием «запомнить ответ», сам является одобрением и сразу попадает в поиск с исходным обращением как источником.
 - Метрика «закрыто агентом» имеет два явных исхода: проверенный ответ без менеджера; КП, автоматически выданное по каталожной цене, с отдельным учётом подтверждения фактической поставки менеджером. Средний первый ответ измеряется до первого видимого ответа и включает уточнения; 2 минуты — целевой уровень, не доказанный результат.
 - Трассы отражают фактические расходы. Режим тени, обещания, настройки, песочница, аудит, аналитика и защита стенда входят в объём; внешние интеграции не объявляются реализованными.
 - Email в веб-канале допускается как адресат обещания доставки документа; входящий/исходящий почтовый канал и реальная отправка писем не входят в объём.

### Вне объёма и запреты

- Телефония, распознавание аудио, входящий/исходящий почтовый канал, Telegram, реальные интеграции с CRM/ERP.
- Полноценный ручной чат менеджера с клиентом не обязателен.
- Микросервисы, мультиагентная схема, полноценный многотенантный биллинг.
- Автоматическая публикация агентских черновиков знаний без одобрения менеджера.
- Использование неподтверждённых цен, условий или наличия; выдумывание источников.
- Перенос готового конкурсного кода, разметки, CSS, токенов стиля или компонентов из системы Ивы.
- Размещение секретов в репозитории, переписке, журнале процесса, свидетельствах проверки или одностраничном описании.
- Локальная разработка не считается публичным стендом и не должна открываться в Интернете без ограничений R17.
- Живой доступ жюри к Web/MAX не считается предоставленным без фактической проверки владельцем.

### Защита публичного стенда

Лимиты стенда: 10 запросов в минуту с IP, 50 новых диалогов в сутки на весь стенд, бюджет модели 300 ₽ в сутки и 30 ₽ в час. `x-forwarded-for` доверяется только при `ALLOW_PROXY_HEADERS=1`; иначе используется адрес соединения. При достижении часового лимита новые диалоги не запускаются, а уже начатый диалог не делает новых вызовов модели и получает сообщение «Лимит демо исчерпан, попробуйте позже». Ошибки поставщика 429/402 не списывают пользовательский лимит повторно; действует один повтор по R16.

**Критерий приёмки:** без кода доступа защищённые маршруты и вызов модели недоступны; новая вкладка не обнуляет счётчики; 11-й запрос с адреса за минуту отклоняется, 51-й диалог за сутки не запускается; бюджет не превышается при конкурентных вызовах. Без `ALLOW_PROXY_HEADERS=1` поддельный `x-forwarded-for` не обходит лимит. После достижения часового предела начатый диалог не делает дополнительных вызовов модели и получает сообщение об исчерпании бюджета. Коды и токены отсутствуют в логах.

 См. `GLOSSARY.md` для канонических терминов предметной области. Документ БЗ и статья БЗ — отдельные сущности с разными API и жизненными циклами. Поиск возвращает только одобренные или опубликованные источники.

 ## Архитектурные ограничения и решения

 - Один процесс, один агент и семь последовательных узлов: понять вопрос → поиск БЗ → проверка каталога → расчёт кодом → проверка полномочий → генерация документа → ответ/эскалация.
 - Модули `catalog`, `knowledge`, `documents`, `policy`, `promises`, `telemetry`; импорт между модулями только через `index.ts`.
 - Адаптеры Web и MAX используют общий контракт приёма/отправки сообщения; ядро не знает о клиентском канале. Снаружи доступен один HTTP API; межмодульные вызовы остаются внутри процесса.
 - Стек: Next.js + shadcn для интерфейса; Node.js/TypeScript для API и ядра; PostgreSQL 16 + pgvector. Единственный источник истины о ценах — каталог.
 - `tenant_id` присутствует во всех доменных таблицах и устанавливается сервером в одной доверенной точке. Продукт развёртывается для одного клиента; мультитенантность/биллинг не требуются (ADR-0016).
 - Бот MAX `@se15151074_bot` подключён через Long Polling `GET /updates`; события `message_created` нормализуются и передаются общему ядру. Проверенный исход `respond` отправляется через `POST /messages`; `escalate` клиенту не отправляется. Живой ответ бота подтверждён; webhook `POST /subscriptions` не входит в критерии демо, т.к. требует публичного HTTPS с доверенным TLS (ADR-0002, ADR-0013).
- Для демо используется `deepseek-v4.1-flash` через OpenCode Go; проверенный резерв — `gpt-5.6-luna`. Эмбеддинги — `qwen3-embedding-8b`, 1536 измерений; маршруты, тарифы и покрытие подписки зафиксированы в ADR-0013. Custom endpoint не заявляется как проверенный резерв.
- Токен MAX выдаёт владелец напрямую; он хранится только в переменных окружения/секретнице и не попадает в файлы, сообщения, свидетельства проверки или описание.
- Тайм-ауты по `docs/HACKATON_BRIEF.md` §6: первый токен — 120 секунд; внутренний шаг — 5 секунд; диалог — не более 300 секунд. При 429 выполняется ровно один повтор через 30 секунд.
- До LLM маскируются ФИО, организация, адреса, телефон, email, ИНН, банковские/паспортные реквизиты и прочие обнаруженные ПД. Модель получает метки; таблица соответствий остаётся серверной. Реквизиты в документы вставляет код; исходящий ответ проходит проверку на утечку ПД.
- Валидатор сверяет все числа в тексте ответа с разрешёнными источниками; `amounts` модели — только дополнительный сигнал. При несоответствии отправка блокируется.
- Ива — только источник идей/UX-референсов; готовые код, разметка, CSS и токены не переносятся (ADR-0006). Одностраничное описание различает код спринта, открытые компоненты с лицензиями и идеи/UX-референсы.
 ## Интерфейсы модулей и инварианты

 Модули представляют внутренние интерфейсы; имена методов и типы request/response exec уточняет в плане/контрактах API, но перечисленные инварианты обязательны.

 ### `catalog`

 Возвращает товар, лицензирование, цену, наличие, срок и опубликованные коммерческие правила с источником/версией данных. Неизвестные поля остаются неизвестными, LLM их не достраивает.

 **Инвариант:** любые цены, налоги и итоговые скидки считает код по каталогу и правилам. Каталог — единственный источник истины о денежных значениях.

 ### `knowledge`

 Выполняет смысловой поиск по опубликованным источникам, возвращает релевантные цитируемые фрагменты и метаданные источника. Читает опубликованные документы и статьи. Неодобренные источники никогда не возвращаются поиском.

 ### `documents`

### `documents`

Создаёт КП и счёт по проверенным данным, расчётам кода и подтверждённым реквизитам; сохраняет связь документа с диалогом для повторного предъявления. Оформление по R26.

**Инвариант:** модель не формирует денежные значения или реквизиты; их рассчитывает и подставляет код.

### `policy`

Проверяет действие, условие, полномочия и результат каталога; возвращает `allow` или `escalate` по R2–R4 и ADR-0019. Неподтверждённые условия не обещаются.

### `promises`

Записывает подтверждённое обещание с диалогом, каналом, адресатом, сроком, ответственным и provenance. Хранит `open`, `done`, `overdue`; открытое также покрывает подготовку/ожидание, просрочка фиксируется при чтении журнала. Внешняя отправка и напоминания не подключаются.

### `telemetry`

Сохраняет упорядоченные шаги, источники, исход, длительность, модель, токены, провайдерскую цену, курс и стоимость; секреты и исходные ПД в трассу не попадают.

## Жизненные циклы базы знаний

### Загрузка документа менеджером

`upload(PDF|DOCX|MD|TXT) → parse → chunks → index → pending → manager approve → published/searchable`.

- Неподдержанный формат или ошибка разбора/индексации оставляет документ недоступным поиску.
- Статус `pending` и другие неутверждённые материалы не возвращаются поиском.

### Ответ менеджера, сохранённый как знание

Разрешённый ответ менеджера, сохранённый действием «запомнить ответ», сам является одобрением и сразу доступен общему поиску с исходным обращением как источником; отдельное одобрение старшего и автоматическое устаревание не требуются (R7, ADR-0019).

### Черновик статьи из диалога

`dialog → article draft → manager review/approve → published/searchable`.

- Агентский черновик недоступен поиску до одобрения и публикации.
- Статья и загруженный документ — отдельные сущности с разными операциями.
- Опубликованная статья фиксируется в `answer.sources` и трассе; URL не показывается клиенту.

## Каналы и исходы

Общий контракт принимает нормализованное сообщение и возвращает проверенный `respond` либо `escalate` с причиной, сводкой и трассой.

### Веб-чат

Подписанная cookie содержит ID диалога, не ПД; идентификация по IP запрещена. Виджет показывает ответ, источники, шаги и стоимость; URL не показываются в клиентском тексте, эскалация видна сторонам.

### MAX

Long Polling передаёт `message_created` в общее ядро. Проверенный `respond` отправляется; `escalate` клиенту не отправляется. Живой тест `@se15151074_bot` обязателен; в режиме тени `POST /messages` не вызывается.

## Режим тени и ответ клиенту

В обычном режиме отправляется только ответ, прошедший проверки полномочий, источников, чисел и ПД. Общий режим тени блокирует отправку Web/MAX и сохраняет результат для менеджера; по умолчанию выключен (ADR-0008). `ESCALATION_MODE=off` допустим только локально без очереди для отсутствующего источника; на стенде используется `notice`, а `on` показывает передачу менеджеру (ADR-0014).
## Допущения и открытые вопросы

Допущение описывает только неизвестное; ответы заказчика и решения владельца перечисляются отдельно и не переобъявляются допущениями.

- **ASSUMPTION A1 — демонстрационные данные:** заказчик предоставил фид `Mindbox.yml.gz.xml`, 495 обезличенных диалогов, шаблон КП и `Базы знаний.docx` со ссылками на Store. Снимок от 25.11.2026: 136 040 предложений, 9 311 категорий, 1 232 вендора, 387 имён параметров, 1 903 038 значений. Остатки, не приведённые в фиде, и иные отсутствующие факты не считаются подтверждёнными; синтетика помечается.
- **ASSUMPTION A2 — фактическая поставка и неуказанные реквизиты:** `available` — значение снимка, не гарантия поставки. Менеджер отдельно подтверждает фактическую поставку; неподтверждённые банковские реквизиты/налоговые и платёжные условия не выдумываются.
- **ASSUMPTION A3 — срок электронной поставки:** «тот же рабочий день» — допущение, заказчик срок не подтверждал; если указан в КП, он явно помечается допущением, а поставку отдельно подтверждает менеджер (R2, R24).
- **ASSUMPTION A4 — язык:** демонстрация на русском языке; другие языки не являются критерием приёмки.
- **ASSUMPTION A5 — реальные внешние интеграции:** CRM/ERP, исходящая почта и телефония не подключаются; история и очередь менеджера работают в прототипе.

**Подтверждённые решения:** Web и MAX обязательны; живой ответ MAX получен. Каталог обновляется раз в сутки ручным запуском, без планировщика; при сбое используется последний успешный снимок (R19, R23). Владелец утвердил лимиты и бюджет стенда (R17, ADR-0009). Коммерческие условия зафиксированы в R2–R4 и ADR-0019.

**Открытый вопрос Q7:** безопасный канал передачи отдельного `MANAGER_ACCESS_CODE` жюри не подтверждён. До закрытия вопроса нельзя заявлять, что доступ жюри к кабинету обеспечен. Неуказанные налоговые/банковские и иные коммерческие поля требуют подтверждённых значений либо эскалации.
## Требования и критерии приёмки

### R1a — клиент знает нужный продукт

Если клиент называет продукт, агент выполняет структурный поиск по датированному фиду, показывает подходящие версии и запрашивает недостающие параметры: количество, срок лицензии и тип развёртывания. Цена и наличие указываются как сведения снимка, а не состояние в реальном времени. По вопросу лицензирования/системных требований при отсутствии ответа в опубликованной БЗ используется только явно заполненное поле карточки с совпавшим `offer_id`; иначе обращение эскалируется. Источник и URL сохраняются в `answer.sources`, трассе и кабинете менеджера, но URL не включается в клиентский текст (ADR-0014, ADR-0015, ADR-0017, ADR-0019).

**Критерий приёмки:** известный продукт без необходимого параметра вызывает уточнение; после уточнения агент выдаёт соответствующую карточку без URL в ответе, а `answer.sources` и трасса содержат источник и URL. При отсутствии карточки/поля или неоднозначном совпадении агент не угадывает и эскалирует.

### R1b — клиент не знает нужный продукт

Агент выясняет задачу клиента и при необходимости уточняет бюджет и инфраструктуру. Затем он подбирает не менее двух подходящих вариантов по каталогу и опубликованным материалам базы знаний, кратко обосновывает различия; источники и ссылки сохраняются в `answer.sources`, трассе и кабинете менеджера, но URL в клиентский текст не вставляется. Формат ответа и запрет URL — по ADR-0014; сценарии подбора и классы маршрутизации — по ADR-0015 и ADR-0017.
### R2 — формирование КП по шаблону ПАО «Софтлайн»
По явному запросу клиента на КП выбранного товара с ценой в каталоге агент автоматически формирует, сохраняет в диалоге и выдаёт КП; предварительного одобрения менеджера нет. Документ содержит наименование заказчика, исходящий номер и дату, официальный логотип и только подтверждённые реквизиты, артикул, наименование, количество, цену, сумму и НДС по каждой позиции, итог, условия оплаты, срок поставки, срок действия и подписанта. Суммы и НДС рассчитывает код. `available=false` не блокирует КП при наличии цены, но остаётся снимком, а не подтверждением поставки. Скидка без купона до 5% включительно разрешена; более 5% и отсрочка эскалируются. Срок электронной поставки «тот же рабочий день» — помеченное допущение, не гарантия; фактическую поставку отдельно подтверждает менеджер. Оформление — по R26 и ADR-0019.

**Критерий приёмки:** выбранная позиция с ценой и запрос клиента автоматически создают КП без предварительного одобрения; без запроса КП не создаётся. При `available=false` КП всё равно формируется, а наличие обозначено датированным снимком. Код независимо рассчитывает сумму и НДС; неподтверждённые реквизиты/условия не подставляются. Скидка свыше 5% и отсрочка эскалируются, менеджер подтверждает только фактическую поставку.

### R3 — формирование счёта

Счёт автоматически формируется и выдаётся только по отдельному явному запросу клиента; предварительного одобрения менеджера нет. Номер, сумма, НДС и разрешённые реквизиты задаёт/проверяет код. `available=false` не блокирует счёт при наличии цены, но менеджер отдельно подтверждает фактическую поставку. Бланк соответствует R26.

**Критерий приёмки:** без отдельного запроса счёт не создаётся; после запроса он выдаётся с уникальным номером, рассчитанными кодом суммой и НДС и проверенными реквизитами. Неподтверждённые поля не выдумываются — выпуск блокируется и обращение эскалируется. `available=false` при наличии цены не блокирует счёт; поставку подтверждает менеджер.


### R4 — эскалация менеджеру
Вопросы маршрутизируются по десяти классам ADR-0017; сомнение классификатора выбирает `out_of_scope`. Полномочия проверяются до ответа по каталогу и до ответа об отсутствии источника; обход допустим только для `greeting`, `self_info`, `company_info` и `howto`. После поиска в БЗ факт о лицензировании/системных требованиях можно взять только из явно заполненного поля карточки с тем же `offer_id`; отсутствующее поле, несовпадение или противоречие ведёт к эскалации. При проблеме после покупки сначала даётся инструкция опубликованной справки; отсутствие инструкции, непокрытый следующий шаг или «не помогло» приводит к эскалации. Неизвестные коммерческие сведения и условия, скидка выше 5%, отсрочка и возврат эскалируются (ADR-0014, ADR-0017, ADR-0019).

**Критерий приёмки:** скидка выше 5% и неподтверждённое коммерческое условие эскалируются до ответа; поле товара используется только при точном `offer_id`, иначе эскалация. Неудачная инструкция после покупки эскалируется. Маршруты соответствуют ADR-0017; только перечисленные классы обходят `policy`.

### R5 — трасса и экономика

Каждый шаг и вызов инструмента записываются в порядке выполнения с результатом, длительностью, моделью, токенами, стоимостью, безопасными ссылками на источники и исходом. Стоимость переводится из фактического `list_cost` провайдера в рубли по конфигурации; отсутствующие данные стоимости нельзя показывать как нулевой расход или как бесплатный вызов. Валидатор извлекает числа непосредственно из текста ответа и сверяет их с разрешёнными значениями каталога/подтверждённых источников; `amounts` от модели — только дополнительный сигнал. Неизвестное или несовпадающее число блокирует отправку и ведёт к эскалации.

**Критерий приёмки:** стоимость трасс пересчитывается по исходному `list_cost` и курсу конфигурации; отсутствие цены не показывается как бесплатный вызов или нулевой расход. Число из текста, отсутствующее в источнике, отклоняется даже при пустом `amounts`; остальные неразрешённые числа также блокируют отправку. Секреты и исходные ПД отсутствуют; экономия по сравнению с ручной работой явно помечается как оценка.

### R6 — загрузка и одобрение документа БЗ менеджером
Менеджер загружает PDF/DOCX/MD/TXT; система разбирает, делит на чанки и индексирует документ, выставляя статус «на проверке». Остальные расширения отклоняются понятной ошибкой. Одобрение менеджера делает документ доступным поиску. Этот поток предназначен для материалов, которые команда сама загружает позднее.

**Критерий приёмки:** до одобрения поиск не возвращает документ, агент отвечает «нет в базе»/эскалирует; после одобрения тот же вопрос получает ответ с цитатой и источником в `answer.sources`, трассе и кабинете менеджера, без URL в клиентском тексте; неподдержанный формат и ошибка разбора/индексации оставляют документ недоступным поиску. Импортированные в рамках R18 исходники заказчика не попадают в статус «на проверке».
### R7 — знания из ответа менеджера и черновик статьи

Кабинет разделяет два потока. Ответ менеджера, который он разрешил действием «запомнить ответ», сам является одобрением: он немедленно становится источником общего поиска для следующих клиентов и сохраняет исходное обращение как источник; отдельное одобрение старшего и срок автоматического устаревания не требуются. Черновик статьи, созданный агентом из диалога, остаётся отдельной сущностью: менеджер проверяет, одобряет и публикует её, и только опубликованная статья доступна поиску (ADR-0019).

**Критерий приёмки:** до сохранения ответа менеджером поиск его не возвращает; после «запомнить ответ» следующий диалог получает ответ с исходным обращением в источниках. Нет дополнительной проверки старшего или срока автоматического устаревания. Черновик статьи остаётся недоступен до одобрения и публикации; отклонённая статья не влияет на поиск.

### R8 — канал веб-чата

Веб-чат начинает и продолжает диалог по подписанной cookie с идентификатором диалога, не определяя пользователя по IP; показывает проверенный ответ, источники, шаги, стоимость и статус эскалации. Визуальное оформление чата, заголовка страницы и favicon соответствует R26.

**Критерий приёмки:** повторный запрос с cookie продолжает тот же диалог; новая/очищенная cookie создаёт новый; два клиента с одним IP не объединяются; эскалация видна клиенту и менеджеру; шапка, заголовок страницы и favicon используют правила R26.

### R9 — канал MAX

Long Polling принимает событие `message_created` реального `@se15151074_bot`, нормализует сообщение и передаёт его в то же ядро, что и веб-чат. Исход `respond` отправляется через MAX; исход `escalate` не вызывает отправку клиенту. Webhook — только будущий вариант развёртывания при наличии доверенного HTTPS.

**Критерий приёмки:** живое входящее сообщение достигает ядра и получает проверенный ответ через MAX; в режиме тени сообщение клиенту не отправляется, в очереди есть черновик/эскалация; тест подтверждает корректную обработку повторного события/идемпотентность или документирует способ предотвращения дубликата. Свидетельства проверки не содержат токенов.

### R10 — режим тени

Менеджер включает/выключает общий для веб-чата и MAX режим тени. Включённая тень блокирует все ответы клиентам и сохраняет черновик/эскалацию.

**Критерий приёмки:** при включённой тени ни веб-чат, ни MAX не получают ответ клиенту; очередь менеджера содержит результат; после отключения один проверенный сценарий может ответить клиенту.

### R11 — управление обещаниями и доставка документов
Разрешённое обещание записывается с диалогом, текстом, каналом (`max` или `email`), адресатом, сроком, ответственным и происхождением. В MAX адресатом является тот же диалог. В веб-чате агент сначала запрашивает email; без валидного адреса обещание не создаётся, отказ ведёт к эскалации и нейтральному уведомлению без срока. Email и таблица соответствий недоступны модели; исходный адрес не попадает в модель, трассу или логи. Для отображения менеджеру адрес хранится в защищённом серверном журнале обещаний и в `conversation_mask`; доступ к нему ограничен менеджерским кабинетом. Повтор собственного email клиенту допустим только для подтверждения адреса в его веб-диалоге (ADR-0014, ADR-0018).

Реальной отправки писем нет: менеджер вручную готовит документ и отмечает отправку. В данных сохраняются статусы `open`, `done`, `overdue`: `open` — обещание исполняется/готовится, `done` — менеджер подтвердил отправку, `overdue` — срок истёк; просрочка переводится в базе при чтении журнала. Во внешние email/CRM/MAX-сервисы обещания не отправляются.

**Критерий приёмки:** MAX создаёт обещание с адресатом-диалогом без email; веб-чат без email не создаёт обещание и эскалирует, с валидным email создаёт запись канала `email` с адресатом и сроком. Исходный email отсутствует в модели, трассе и логах; он доступен только серверной записи для менеджерского кабинета. Менеджер видит канал/адресата и статусы `open`/`done`/`overdue`, вручную отмечает отправку. Внешних интеграций доставки нет.

### R12 — настройки агента, песочница и аудит

Менеджер может управлять принятой конфигурацией агента (поставщик/модель/endpoint, инструменты/навыки/MCP, системная инструкция/параметры/ограничения, режим тени); безопасно проверять её в изолированной песочнице без отправки клиенту; видеть историю проверок с конфигурацией, оценкой и стоимостью, а также аудит изменений. Кабинет менеджера оформлен по R26.

**Критерий приёмки:** запрос из песочницы не меняет клиентские диалоги/статистику и не отправляется во внешний канал; изменение применяется к следующему новому диалогу; значения секрета скрыты и не записываются в трассу/аудит; каждая настройка в интерфейсе работает либо явно помечена как нереализованная; UI кабинета использует web-палитру и типографику R26.

### R13 — аналитика

Менеджер видит фактические по трассам ответы/эскалации, токены/стоимость, длительность и пробелы БЗ. «Закрыто агентом» состоит из двух раздельных случаев: ответ без менеджера; автоматически выданное КП по цене каталога после одного действия менеджера по подтверждению поставки. Средний первый ответ измеряется от входящего до первого видимого ответа, включая уточнение; 2 минуты — цель, не гарантированный результат. Демо/синтетика и оценочная экономия помечаются (ADR-0019).

**Критерий приёмки:** контрольные трассы дают независимый пересчёт двух видов «закрыто агентом», затрат/токенов и среднего времени до первого видимого ответа. Синтетика/демо отделены от фактической эксплуатации; секретов и исходных ПД нет.

### R14 — персональные данные и маскирование

На входе маскируются ФИО, организация, адрес, телефон, email, ИНН, банковские и паспортные реквизиты и иные обнаруженные персональные данные. Модели передаются только метки; таблица соответствий хранится отдельно и никогда не попадает в модель или трассу. Код подставляет подтверждённые реквизиты в документы; перед клиентской отправкой выполняется проверка на утечки (ADR-0004).
**Критерий приёмки:** тестовые примеры с каждым поддержанным классом персональных данных показывают в запросе к модели только метки; таблица соответствий и токены не передаются; исходящая проверка блокирует незамаскированные значения; тестовые реквизиты добавляются документу только кодом после генерации.

### R15 — единая установка на одного клиента

Продукт развёртывается одной установкой для одного клиента. `tenant_id` — зарезервированное серверное поле; переключение арендаторов, межарендаторное управление и биллинг не входят в объём (ADR-0016).

**Критерий приёмки:** все данные относятся к одному клиенту; `tenant_id` устанавливается сервером и не переключается клиентом. RLS и сценарии межарендаторной изоляции не требуются.

### R16 — тайм-ауты и повторные вызовы модели

Предел ожидания первого токена — 120 секунд; внутреннего шага — 5 секунд; всего диалога — 300 секунд. При HTTP 429 выполняется ровно один повтор через 30 секунд. Для демо используются `deepseek-v4.1-flash` через OpenCode Go; проверенный резерв — `gpt-5.6-luna` по OpenCode Go (ADR-0007, ADR-0013). Отказы доступа, региона, модели, исчерпание тайм-аута/повтора ведут к безопасной эскалации.

**Критерий приёмки:** управляемый тестовый провайдер возвращает 429/тайм-аут; система делает ровно один повтор после 429 и затем эскалирует, не отправляя выдуманный ответ. Реальные ошибки внешнего провайдера намеренно не создаются.
### R17 — защита публичного стенда

Клиентский код доступа хранится в окружении; серверная проверка выдаёт подписанную cookie, связанную с действующим кодом, а смена кода отзывает старые cookie. Кабинет менеджера защищён отдельным `MANAGER_ACCESS_CODE` и отдельной cookie. Безопасный канал выдачи кода жюри остаётся открытым вопросом Q7; нельзя считать доступ жюри к кабинету предоставленным до его подтверждения. Клиентская страница, защищённые API и отправка в MAX недоступны без проверки доступа. Оформление страницы доступа соответствует R26.

Лимиты стенда: 10 запросов в минуту с IP, 50 новых диалогов в сутки на весь стенд, бюджет модели 300 ₽ в сутки и 30 ₽ в час. Заголовок `x-forwarded-for` доверенный только при `ALLOW_PROXY_HEADERS=1`; иначе для лимита используется адрес соединения. При достижении часового предела новые диалоги не запускаются; уже начатые завершаются без новых вызовов модели, клиент получает «Лимит демо исчерпан, попробуйте позже». Ошибки поставщика 429/402 не списывают пользовательский лимит повторно; действует ровно один повтор по R16. Коды и токены не попадают в журналы.

**Критерий приёмки:** без действительного кода доступа защищённые маршруты и вызовы модели недоступны; новая вкладка не обнуляет счётчики; 11-й запрос с одного адреса за минуту отклоняется, 51-й диалог в сутки не запускается, часовой бюджет не превышается даже при параллельных вызовах. При отсутствии `ALLOW_PROXY_HEADERS=1` подмена `x-forwarded-for` не обходит лимит; при установленном флаге используется адрес прокси. После часового предела уже начатый диалог не вызывает модель повторно и получает понятное сообщение. Секреты отсутствуют в журналах; доступ к кабинету менеджера отдельно защищён.
### R18 — импорт предоставленных заказчиком страниц базы знаний

Ссылки `https://docs.softline.com/ru-ru` и `https://store.softline.ru/delivery_info/` из `Базы знаний.docx` являются предоставленными заказчиком источниками. Импортёр обходит восемь корневых разделов (`id`, `lk`, `subscriptions`, `vendors`, `checkout`, `merchant-portal`, `payment`, `allsoft`) в ширину до глубины 3, удаляет дубликаты URL, соблюдает интервал не менее 1 секунды и отправляет понятный `User-Agent`, кэширует исходный HTML и сохраняет для индекса только извлечённый текст. При первом 429/5xx обход останавливается с причиной и сохраняет уже собранные страницы; следующий запуск продолжает работу с кэшированными страницами, не обращаясь к сайту повторно за ними. Сохраняются заголовок, путь разделов, основной текст, URL источника и дата обхода. Чанки размером 800–1200 знаков содержат заголовок, путь разделов и URL. Импортированный источник получает статус `approved_by_customer` и провенанс, поэтому доступен поиску без одобрения менеджером; пользовательские документы и статьи по R6/R7 по-прежнему требуют одобрения.

**Критерий приёмки:** обход посещает только восемь заданных корней и их ссылки до глубины 3; проверка логов подтверждает дедупликацию URL, не более одного сетевого запроса в секунду и наличие `User-Agent`. После искусственного 429/5xx обход останавливается, сохраняет частичный результат, а повторный запуск использует кэш и не запрашивает закэшированные страницы снова. Тест проверяет сохранение заголовка, пути, основного текста, URL и даты в чанках 800–1200 знаков. Поиск возвращает заказчицкий источник со статусом `approved_by_customer` без одобрения; документ R6 и статья R7 остаются недоступны до одобрения.

### R19 — импорт товарного фида и структурный поиск каталога
Импортируется датированный снимок заказчика `Mindbox.yml.gz.xml` потоково. Снимок от 25.11.2026 содержит 136 040 предложений, 9 311 категорий, 1 232 вендора, 387 имён параметров и 1 903 038 значений параметров. Отдельный снимок по живому URL, проверенный 26.11.2026, содержал 135 863 предложения и 513 категорий; эти разные снимки не объединяются и не усредняются (ADR-0010, `.specs/revisions/2026-11-27-opencode-catalog-revision.md`). 44 601 позиция в приложенном снимке имеет `available=true`, 55 771 — положительную цену. Около 200 000 — приблизительная оценка заказчика. Ключ импорта — `offer/@id`; `vendorCode` не гарантированно заполнен и уникален. Категории сохраняются с путём. Поиск выполняется структурно по идентификатору, названию, вендору, категории, доступности и параметрам; векторный индекс применяется только к БЗ и статьям. Цена и доступность относятся к датированному снимку, а не подтверждают текущие коммерческие условия.

**Критерий приёмки:** импорт потоковый и идемпотентен по `offer/@id`; измеренные числа сверяются с выбранным снимком и его датой/хешем, разные снимки не смешиваются. Отсутствие или неуникальность `vendorCode` не сливает позиции. Поиск по атрибутам структурный; у каталога нет векторного индекса.

### R20 — таксономия намерений обращений

Классификатор поддерживает девять категорий обращений из 495 обезличенных диалогов заказчика: «Просто цена конкретного товара» (131), «Прочее (покупка)» (120), «Счёт/КП как документ» (76), «Конфигурация/спецификация» (70), «Доступность вендора» (45), «Физлицо/самозанятый/срок» (27), «Скидки/льготы/спецусловия» (15), «Госзакупки/процедуры» (8), «Follow-up/не дозвонился» (3). Это аналитические категории обращений из миграции 170; они не являются десятью классами маршрутизации ADR-0017. Класс маршрутизации записывается в трассу и выбирает одну дорожку; аналитическая категория используется для частот и пробелов БЗ. Маппинг категорий на классы не 1:1 и описан в ADR-0017.

**Критерий приёмки:** тестовый набор покрывает все девять аналитических категорий; каждое новое сообщение получает один класс маршрутизации из закрытого списка ADR-0017 и одну аналитическую категорию, когда она определима; смена темы обновляет категорию и сохраняет историю; неоднозначный класс приводит к `out_of_scope`, уточнению или эскалации. Маршруты классов не смешиваются.

### R21 — масштаб нагрузки и демонстрационная экономика

Около 500 обращений в день — оценка заказчика для будущей проекции, а не критерий нагрузки или измеренный факт. Фактические расходы пилота считаются по трассам и тарифам провайдера; проекция на 500 обращений в день требует отдельно помеченных допущений о токенах и доле эскалаций. Наблюдавшиеся цены отдельных ответов не являются ценой полного диалога или гарантированным тарифом.

**Критерий приёмки:** дневные/месячные проекции пересчитываются из фактической стоимости измеренных ответов и явно указанных допущений. Демонстрационные измерения отделены от проекции; нагрузка 500 обращений не называется проверенной без нагрузочного испытания.

### R22 — происхождение импортированных данных

Для каждого источника знаний и каталога сохраняются URL/путь или имя файла, дата получения, идентификатор снимка и статус. Предоставленные заказчиком материалы БЗ и фид помечаются `approved_by_customer`; пользовательские загрузки и черновики статей следуют R6/R7; синтетические записи имеют отдельную пометку.

**Критерий приёмки:** ответ и трассировка содержат ссылку и дату/идентификатор снимка; поиск различает одобренные источники заказчика, опубликованные материалы команды и синтетику; новый снимок не удаляет историю предыдущего происхождения.

### R23 — ежедневное обновление каталога

Источник каталога — `https://store.softline.ru/feeds/Softline.yml.gz`; обновление по регламенту заказчика выполняется раз в сутки вручную. Планировщик в спринте не создаётся. При недоступности URL используется последний успешный снимок, а отчёт показывает его дату и хеш.

**Критерий приёмки:** ручной запуск потоково скачивает и распаковывает gzip либо использует последний снимок; повторный импорт идемпотентен по `offer/@id`; дата и хеш видны; автоматического расписания нет.

### R24 — срок электронной поставки в КП

Срок электронной поставки «тот же рабочий день» — допущение по преобладанию электронной поставки, а не подтверждённый заказчиком факт и не гарантия (ответ заказчика о частоте обновления фида не подтверждает срок поставки). Если этот срок показан в КП, он явно обозначается как допущение; фактическую поставку менеджер подтверждает отдельно. Требование не вводит предварительное одобрение каждого КП, которое иначе автоматически выдаётся по R2 (ADR-0019).

**Критерий приёмки:** срок электронной поставки нигде не маркируется подтверждённой гарантией; в КП он видимо помечен как допущение. Неизвестный тип поставки не заполняется догадкой и требует эскалации либо подтверждения менеджера. Выдача КП по R2 не блокируется предварительным одобрением менеджера.
### R25 — двухволновая параллельная реализация

Волна 1 работает по замороженным `docs/api-contract.md` и `docs/data-model.md` в изолированных каталогах: тикет 01 (ядро), 02 (КП/счёт), 05 (MAX), 11 (защита стенда), 12 (импорт фида), 13 (импорт БЗ). Эти тикеты не зависят от реализации друг друга. Волна 2: режим тени, обещания, настройки агента, аналитика и тикет 10 по надёжности после 01; мультитенантная изоляция не входит в план. Решение об однотенантном развёртывании — ADR-0016. Контракт, модель данных, роутер и ядро меняет только exec; миграционные диапазоны закрепляет exec. Тяжёлые импорты фида и сайта запускаются последовательно на стенде 4 vCPU/8 ГБ.

**Критерий приёмки:** матрица требований связана с тикетами; замороженный контракт обозначен входным условием, а не тикетом-блокером; первая волна содержит шесть независимых тикетов; зависимости второй волны не образуют циклов; у каждого среза собственные каталоги/миграции, команда проверки и свидетельства.

### R26 — фирменный стиль Softline

Веб-интерфейсы чата, кабинета и страницы доступа используют UI-палитру Softline: акцент `#A50F2D`, hover `#D20B33`, фон `#F0F2F6`, основной текст `#212424`, вторичный текст `#40454E`, разделители `#D2DCE5`. Печатные документы используют корпоративную палитру `#A20C33`, `#A6A8AB`, `#2396D3`, `#686968`; основной текст корпоративного бланка чёрный. Для веба и PDF используется Montserrat со стеком `Montserrat, "Segoe UI", system-ui, sans-serif`; Segoe UI допускается только как системный fallback и не встраивается в web. В шапке веб-интерфейсов размещается официальный логотип «Софтлайн Решения + SOFL». Используется только предоставленная цветная версия на светлом фоне или белая на бордовом/тёмном фоне; запрещено менять цвета, пропорции, ориентацию, добавлять тени, обводки, эффекты или собственные варианты. Охранное поле вокруг логотипа — не меньше высоты самого логотипа. Корпоративный бланк КП и счёта содержит логотип и подтверждённые реквизиты в шапке, слоган «Мы знаем. Мы можем.» в подвале. Страница доступа, favicon, заголовок страницы и аватар MAX-бота используют утверждённые брендовые материалы. Титульный слайд демо-описания делается из корпоративного шаблона 16:9; конечный слайд шаблона не меняется.

**Критерий приёмки:** автоматизированная проверка вычисленных CSS custom properties подтверждает заданные web-цвета и стек шрифтов, а CSS не содержит хардкод цветов вне UI-токенов; Segoe UI не встраивается в web. Визуальная проверка чата, кабинета и страницы доступа подтверждает фирменную палитру и официальный логотип в разрешённой версии. Проверка геометрии макета подтверждает свободное поле логотипа не меньше его высоты. Проверка PDF КП/счёта подтверждает корпоративную палитру, Montserrat, чёрный основной текст, официальный логотип и подтверждённые реквизиты в шапке, слоган в подвале; неподтверждённые контакты не подставляются. Favicon и MAX-аватар используют только утверждённые файлы/варианты логотипа; презентационный титульный слайд использует корпоративный PPTX, сохраняет формат 16:9 и неизменный конечный слайд. Источники: `docs/лого софтлайн/Softline Guideline 2025 (1).pdf`, предоставленные PNG/EPS-логотипы и `docs/лого софтлайн/Шаблон СЛ Решения расширенный 2026 (1).pptx`; решение — ADR-0012.
